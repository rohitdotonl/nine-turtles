# 0256: MCP's stateless version, beside the old ones

**In one line:** `/mcp` also speaks MCP 2026-07-28 (no `initialize`; each request carries its version and capabilities in `_meta`, matched by `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers; answers carry `resultType` and `serverInfo`; the discover method (server/discover); a version it doesn't speak gets 400 with -32022 and the list), while 2025-11-25, 2025-06-18 and 2025-03-26 work as before; a `resource` naming another server is refused (RFC 8707); a bad ticket's 401 says `invalid_token`; and the 15-day MCP check reads the specification from GitHub, where its runs can reach it

*11 November 2026.*

Rohit's to-do (6 November 2026): "Implement MCP cleanly with the best
industry standard. Also make sure that you keep an eye on how MCP standards
evolve over time." What was built in October (decision 0111) was sound and
followed 2025-11-25, but MCP published a new version on 28 July 2026 that
nine turtles didn't speak yet.

## What changed in the standard

2026-07-28 makes MCP stateless: no opening `initialize`, no sessions, no
`ping`. Every request says its version and what the assistant can do in
`params._meta`, and on HTTP repeats the version, the method and (for a tool
call) the tool's name in headers, so a proxy can route on them; the server
must refuse a request whose headers and body disagree (400, -32020). Every
answer says it's `complete` and who answered; the tool list says how long it
may be kept (`ttlMs`, `cacheScope`); the discover method (server/discover) lists the versions,
and a version the server doesn't speak gets 400 with -32022 and that list.
Dynamic client registration (RFC 7591) is now "deprecated" in favour of
client ID metadata documents, but stays in the standard for at least 12
months.

## What nine turtles does

- **Both eras on one `/mcp`** (`server/src/mcp/protocol.rs`). nine turtles
  never kept a session, so serving both is a few checks, not a second
  server: a request with the version in `_meta` is the new way; one opening
  with `initialize`, or carrying no `_meta`, the old way, answered exactly
  as before (no header at all still means 2025-03-26, as the standard
  allows). Assistants move over when they're ready; none is left behind.
- **Who answered.** `serverInfo` now also has a description, the website
  and the turtle icon, so assistants can show it beside the tools.
- **Tickets only for this server** (RFC 8707). An assistant names the server
  it wants a ticket for; one naming another server is refused (the
  "Connect" page shows its usual "this link isn't right", and `/oauth/token`
  answers `invalid_target`). Tickets here only ever opened `/mcp`, so this
  closes a door nobody could use, but it's what the standard asks.
- **A bad ticket says so** (`error="invalid_token"` in the 401's
  `WWW-Authenticate`), so an assistant knows to refresh rather than start over.

## What it deliberately doesn't do

- **The `Origin` rule.** The standard says a server must refuse a
  request whose `Origin` is "invalid", against "DNS rebinding" (a web page
  tricking a browser into talking to a server on the reader's own
  computer). nine turtles isn't on the reader's computer, `/mcp` takes only
  tickets (never the cookie), and it sends no permission for other sites'
  pages to call it, so a browser never delivers another site's request.
  Assistants' own servers sometimes send an `Origin`; refusing them would
  break real assistants for no protection, so any `Origin` is still accepted
  (`security.rs`).
- **No scopes.** A connected assistant may use every tool, as agreed in
  decision 0111, so there's nothing to ask for step by step.
- **Structured results** (`structuredContent`, `outputSchema`) stay optional
  in the standard; the tools' answers remain JSON as text, which every
  assistant reads.
- **Client ID metadata documents** (the new way to sign in, where nine
  turtles would read a small file from the assistant's own site) need a new
  kind of visit, so they're the owner's choice and a change of their own.
  The old way (dynamic registration) stays: Cursor, for one, knows only it.

## Keeping up

The 15-day MCP check (`docs/operations/mcp-check.md`) already existed, but
its runs can't reach `modelcontextprotocol.io`, which is likely why it didn't
flag 2026-07-28. It now reads the specification from its GitHub repository,
and any new version gets at least an issue for the owner, even when no
assistant requires it yet.

**Revisit when:** a new MCP version comes out, or when the big assistants
all sign in with client ID metadata documents and dynamic registration can
go.
