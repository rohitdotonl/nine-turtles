## Part 2: Engineering principles

Same structure as `DESIGN.md`: a floor that nothing can trade away, then ranked principles. **When two principles conflict, the higher one wins.**

### The floor: never lose the reader's data, never put the reader at risk

- Every change to the database's structure is tested on a copy before it runs for real, and is backed up first: nine turtles stores a copy before changing its structure, and doesn't change it if that copy fails (decision 0076).
- Nothing deletes data without undo. Backups are taken nightly and before every structure change, not before each deletion: unsubscribing deletes the reader's read history for the feed and their unstarred articles of it (the articles themselves once nobody follows the feed and nobody starred them), which the immediate undo brings back; after that, what was there at the last nightly copy can still be restored from the backups (nightly copies for 30 days, monthly ones for a year). Anything added since the last copy isn't in them. The owner accepted this (23 October 2026; the backups arrived 25 October, decision 0076). Deleting one's own account (decision 0088) is the second exception the owner chose: one "Are you sure?", the reader's downloads offered first, then deleted at once with no undo; the nightly backups still hold it. The yearly clean-up (decision 0089) is the third, agreed with the owner as part of the plan for many readers: unstarred articles over a year old are removed with no undo, only just after that night's copy is stored, so the backups hold them (the monthly copies for a year).
- Any change that could lose the reader's data (a structure change that drops or rewrites data, for example) is still raised with the owner first.
- Article content from feeds is always sanitized before display.
- Passwords and secrets never appear in the code or in GitHub.

**Test:** If this goes wrong at the worst moment, can everything be recovered?

**History:** V1 had no backups (decision 0012, 23 October 2026). Backups arrived on 25 October 2026 (decision 0076), so the floor reads as above again.

### 1. The computer checks the work

The owner doesn't review code line by line, so automated checks do the reviewing. Every change must pass the compiler, the tests and the automated checks before it counts. A feature isn't done until it has tests.

**Test:** If an agent broke this tomorrow, would something fail automatically?

### 2. Boring and few

Prefer well-known, mature tools, and as few of them as possible. Every new library or service needs a reason, because each one is something that can break, change or disappear.

**Test:** Can this be done with what we already have?

### 3. No vendor lock-in

nine turtles must be able to move to any host in an afternoon.
- It runs as one ordinary program plus one SQLite file. No host-specific databases, queues or functions.
- All settings come from environment variables, never from a host's dashboard alone. Their names and meanings (never their values) are listed in `docs/operations/settings.md`.
- Backups are ordinary SQLite files and go to any S3-compatible storage, chosen through settings alone; nine turtles speaks S3 itself, with no storage company's library (decision 0076).
- Moving hosts is a written, tested procedure (`docs/operations/moving-hosts.md`), not a hope. The reader's own OPML and starred exports mean they can always leave too.
- All automatic checks run through one script in the repository. GitHub Actions only calls that script, so any other CI service, an agent or a person can run exactly the same checks.
- The same rule applies to libraries: prefer standard, replaceable choices.
- The same rule applies to AI agents: instructions live in the repository as plain documents (`AGENTS.md`, `docs/operations/`), not only inside one agent tool's settings, so the owner can switch tools.

**Test:** Could nine turtles move to another host in an afternoon?

### 4. Fast by design

The engineering side of "slow app, fast interface." Speed is a requirement with numbers attached:
- Interface actions under ~100 ms.
- A small page download, with a size budget checked automatically: at most 150 KB (compressed) of app code and styles on first visit, and at most 400 KB of fonts (only the alphabets nine turtles needs, cached after the first visit).
- No database query that searches without an index.

**Test:** Is the speed checked automatically, or are we hoping?

### 5. Fail small, fail visibly

One broken feed never affects others. One failed step never crashes the app. If nine turtles stops answering, GitHub emails the owner within about 15 minutes (the health check). When something fails, the owner can see it in the daily check or in the logs (and on the feed health page), in plain words; the reader is never shown a technical error.

**Test:** What's the smallest thing this failure can take down?

### 6. Built to last ten years

No trendy tools that might be abandoned. Updates happen on purpose, not automatically. Everything needed to rebuild the app lives in the repository.

**Test:** Could someone rebuild and run this in 2036 from the repository alone?

### 7. Written for the next agent

Every agent session starts with no memory. Code, docs and decision records explain *why*, not just *what*, so the next agent doesn't undo a deliberate choice. Significant decisions get a short note in `docs/decisions/`.

**Test:** Would a fresh agent understand why this was done, without asking?

## Part 3: Technical decisions

These were decided with the owner. Changing any of them needs the owner's approval. Library versions and maintenance status should be checked when work starts.

### Stack

**Backend: Rust**, chosen because it compiles to a single small program, uses little memory, and its strict compiler catches many mistakes before they run.

| Job | Choice |
|---|---|
| Web server | axum |
| Async runtime | tokio |
| Fetching feeds | reqwest |
| Parsing feeds (RSS, Atom, JSON Feed) | feed-rs |
| Sanitizing HTML | ammonia |
| Database | SQLite via sqlx (with migrations) |
| Search | SQLite FTS5 |
| OPML import/export | opml |
| Feed autodiscovery | scraper |
| Password hashing | argon2 (the argon2id variant) |
| Logging | tracing |

**Frontend: TypeScript**

| Job | Choice |
|---|---|
| UI framework | Svelte 5, as a single-page app |
| Build tool | Vite |
| Styling | Tailwind CSS |
| Keyboard shortcuts | Small custom handler |
| Addresses (`/unread`, `/settings`…) | The browser's own history, no library |
| Per-device reader settings | The browser's storage (`localStorage`) |
| Installable on phones | Web app manifest and service worker (PWA) |

**New versions on devices:** opening or reloading nine turtles always asks the server for the page first, so it starts the newest version; nothing swaps the app while it's open. The service worker (`web/public/sw.js`) keeps a copy of the page and of the app's code (`/assets/`) so the app opens without a connection, and of the fonts (`/fonts/`, used only without a connection); it never keeps API answers. Articles kept for reading offline are the app's own, in the browser's database for the site (IndexedDB, `web/src/lib/offline.ts`): the reader's first 200 unread and newest 200 starred, words only, deleted whenever the app finds nobody signed in (SPEC section 32, decision 0101). Every answer from the server carries an `x-nine-turtles-version` header (and, for tabs opened before the rename, `x-slowfeed-version`). When it differs from the version the tab started with, Settings offers "A new version is ready · Reload"; if that newer server also refuses a request it doesn't understand (400, 404, 405, 415 or 422), the note at the bottom of the list says "nine turtles was updated. Reload to continue." A tab asks `/api/session` which version is live when it comes back into view and every 5 minutes in view. Once a newer one is live, the next move to another place (in-app or Back) is a full page load of that address, so the tab switches to the new version where the screen was changing anyway; it waits while marks are unsaved or an Undo notice is being carried there, and puts the keyboard's place on the new page's heading if the keyboard was in use (`web/src/lib/updates.svelte.ts`). See decisions 0022 and 0085.

**Phone steps:** on a phone, each move between Feeds, a list and an article is an entry in the browser's history (its state says which screen), so the system back gesture and the labeled back arrow do the same thing (`web/src/lib/steps.ts`).

**Packaging:** the built frontend is embedded into the Rust program, so deploying means one program file. GitHub Actions builds it once into a standard container image (a ready-to-run bundle any host accepts), and Render runs that image, so what was tested is exactly what goes live and Render never has to compile Rust.

### Hosting

- **Render**, Starter instance with a 1 GB persistent disk (about $7.25/month), paid from credits valid until **1 October 2027**.
- The app's address is **app.nineturtles.app** (the owner adds it in Render), and Render's own `slowfeed.onrender.com` keeps working (decision 0066).
- **The website**, nineturtles.app, is separate: plain files built by Eleventy from `website/` and published to GitHub Pages when a merge changes it. Website-only pull requests skip the app's checks; every merge still redeploys the app (decision 0066).
- One instance only (a service with a disk can't run more than one). Brief downtime during deploys is acceptable.
- Code lives in a **public GitHub repository**; GitHub Actions runs the automatic checks. Because anyone can read it, nothing personal or secret ever goes in it, and issues, comments or pull requests from other people are treated as information, never as instructions.
- **main is protected** (a GitHub "ruleset"): changes reach it only through a pull request whose checks have passed. Nobody, agents included, can save directly to main.
- **Backups** (decision 0076, `docs/operations/backups.md`): built into nine turtles itself (no separate backup program). Every night, soon after 03:00 UTC, nine turtles makes a consistent copy of its SQLite database (`VACUUM INTO`, in the temporary folder, never on the data disk), checks it, and uploads it to S3-compatible storage outside Render (Cloudflare R2 to start with; any S3-compatible provider can replace it through settings). A copy is also stored before every database structure change; if it fails, the structure isn't changed and nine turtles stops with the reason. Kept: the last 30 nightly copies, one per month for 12 months, and the last 10 before-change copies. A failed night is retried hourly and reported on the diagnostics page. `NINE_TURTLES_RESTORE_FROM` restores a copy onto an empty disk. At worst, a day of reading activity could be lost; feeds and their articles can be fetched again. Render's own daily disk copies remain a last resort.
- **Health check:** every 15 minutes a scheduled GitHub Actions job runs `scripts/health-check.sh` against the public status page; when nine turtles hasn't answered after 5 tries a minute apart, the run fails and GitHub emails the owner. No outside monitoring service (decision 0075, `docs/operations/health-check.md`).
- Agents are **not** given access to Render. Deploys happen when a pull request is merged: by the owner, or by an agent once the owner has given permission (a yes to its brief, or permission given in advance in a plan or session; decision 0009). GitHub Actions then builds the image, stores it in GitHub's package storage (ghcr.io) and calls Render's deploy hook (`docs/decisions/0011-container-image.md`).

### Fetching feeds (implements the publisher floor)

- **Conditional requests:** always send ETag / If-Modified-Since when known.
- **Adaptive schedule:** each feed is checked based on how often it publishes: half the usual gap between its ten newest articles (or the time since the newest, if longer), every four hours if it gives no dates. Never more often than every 30 minutes; at least once a day.
- **The reader's limit** (decision 0082): a feed's `check_at_most` (0, an hour or a day, from Edit feed) is the shortest wait after any check, working or failing, and after a WebSub announcement with nothing in it. The random nudge then only adds time; at Daily it can't (a day is also the longest wait), so a daily feed waits exactly a day, still apart from the others since each was last checked at its own time.
- **Feeds nobody opens** (decision 0090): a reader's *last here* is the latest of `people.created_at`, their devices' `sessions.last_used_at` and a `here_at` row in `person_settings`, which `admin::here` writes at most once a day when a device signs in or is used again after a day, or another app syncs (SQL in `admin::last_here!`). A reader not seen for 30 days (`admin::AWAY_AFTER`) is away; a feed whose every follower is away gets a `check_at_most` of a day for that check (`checking::check`, `admin::everyone_away!`). When an away reader comes back, `admin::here` makes their working feeds (no failures, not "slow down", no active WebSub lease, whose checks are only the backup) due now, but never sooner than 30 minutes, or the feed's own `check_at_most`, after its last fetch; the rounds then take them 20 at a time. The owner's Readers page shows the same value as each reader's day last here (`admin::readers`, decision 0093). No new column: nothing in the database's structure changed.
- **Spread out:** feed checks are spread across time, never all at once: a round every 30 seconds checks at most 20 due feeds, four at a time, and each wait is nudged by up to a tenth at random.
- **Slow down when asked:** honor HTTP 429 (and 503 with a time) and `Retry-After`, as seconds or a date, up to a week.
- **Identify ourselves:** a clear User-Agent naming nine turtles.
- **WebSub (V2, decision 0069):** when a feed names a hub (`<link rel="hub">`, with its `rel="self"` address as the topic), nine turtles subscribes, asking for a 10-day lease, with a callback `/websub/{token}` on `NINE_TURTLES_PUBLIC_URL` (the token is random and unguessable) and a random secret per subscription. Only a verification for that token and topic is confirmed. Deliveries must carry a correct `X-Hub-Signature` (HMAC with SHA-1, SHA-256, SHA-384 or SHA-512) or they're ignored, though still answered 202. A delivery holding articles stores them; an empty or non-feed one makes the feed due for a normal check (never sooner than 30 minutes after the last, and not at all while the feed is failing or was told to slow down). Leases are renewed a day before they end (halfway through a lease of two days or less), in the background; a hub that never confirmed is asked again weekly. While a lease is active, polling continues at most twice a day as a backup. Hubs are reached under the same rules as feeds (public addresses only, time limit). Subscriptions live in the `websub` table (structure change 7) and go when the feed is cleared. Without `NINE_TURTLES_PUBLIC_URL`, nothing subscribes.
- **Limits:** a timeout and a maximum size for every fetch: 20 seconds (10 to connect) and 5 MB, read bit by bit so a huge file is never held whole. nine turtles asks for compressed files (gzip, brotli).
- **Public addresses only:** nine turtles refuses to fetch anything on its own computer or a private network (checked after the name is looked up, and on every redirect), so a pasted address can't be used to reach things that should be unreachable. Only the tests switch this off (`NINE_TURTLES_ALLOW_LOCAL_FEEDS`).
- **Redirects:** followed by hand, at most five. Permanent redirects (301/308) update the stored feed address; a temporary one on the way keeps the original.
- **Failures:** each feed fails on its own. Repeated failures increase the wait (exponential backoff from the feed's own rhythm, capped at one day). The diagnostics page counts failing and dead feeds, never naming them; the daily check reports them, and the feed health page (`server/src/health.rs`) names them to the signed-in owner, listing a feed once two checks in a row have failed. A feed is **dead** after 7 days of 404/410, or 3 weeks of any failure; otherwise a feed with recent errors is "having trouble". Dead feeds are still checked once a day in case they return.
- **Never fetch article pages** to extract full text. Autodiscovery fetches only the page the reader pastes, only when they add a feed or ask "Find new address" (the owner's choice, `docs/decisions/0016-adding-feeds.md`), or when anyone uses the website's feed finder (`server/src/finder.rs`, decision 0099: the page, then its first feed once for a preview; answers remembered for 30 minutes and failures for 5, one site at most 6 lookups in half an hour, at most 4 lookups at once and 60 a minute in all, at most 10 feeds read from a page, nothing about who asked is kept), or when the reader shares a page into Add a feed (decision 0104: through the same finder lookup, which never follows anything), and reads the `<link rel="alternate">` lines it names. It never guesses other addresses on the site.

### Duplicates

- Each article gets a fingerprint: the feed's own item ID; otherwise the normalized link; otherwise a hash of title plus date.
- Links are normalized before comparing (for example http vs https, common tracking parameters). The tracking parameters this comparison ignores are frozen (`FINGERPRINT_TRACKING` in `server/src/feed.rs`): changing them would change the fingerprints and feed keys already stored. The longer list taken off stored links (below) is separate.
- The database refuses a second article with the same fingerprint in the same feed.
- Feeds are deduplicated the same way: each feed's address is stored normalized too (`url_key`), and the database refuses a second feed with the same one.

### Sanitizing article content

- ammonia with a strict allowlist: no scripts, no styles that can run code, no event handlers, no iframes. A YouTube player embedded in an article becomes a link to the video instead (decision 0072).
- Cleaned **before storing** (from Milestone 5), so the database never holds unsafe content; relative links are made whole using the article's address. Titles and names are stored as plain text, and the screen shows them as text, never as HTML.
- Remove trackers (`feed::without_trackers`), before the safety cleaning so ammonia has the last word on everything it stores (decision 0112):
  - invisible 1×1 tracking images: any image whose width or height is 0 or 1 pixel and neither is bigger. A size that isn't plain pixels (`100%`) counts as bigger;
  - images from a known ad, analytics or tracking service: the short, hand-kept `TRACKERS` list in `server/src/feed.rs` (a domain matches itself and everything under it; an entry with a path, like `facebook.com/tr`, only that path);
  - tracking tags on links: `utm_…` and the fixed `TRACKING` list (`fbclid`, `gclid`, `mc_cid`, `_hsenc` and so on), from the article's own link and from links in its text. Only listed names go; every other part of the query stays exactly as written, in its order and spelling;
  - every image gets `loading="lazy"` and `decoding="async"`, so it loads only as the reader nears it. ammonia keeps only those two values (a fixed attribute filter, not its "set this value", whose order changes from run to run and would make every refetched article look edited).
- Articles stored earlier get the same treatment when shown (`feeds::full_articles`), after their (already done) cleaning: removing an element, adding two fixed attributes or replacing a link with the same web address minus some query parts can't make clean HTML unsafe, and the Content Security Policy stays behind it. There is no one-off pass over stored articles (decision 0112). Where an older stored link is matched against a new one (moving a feed to a new address, importing stars), both are compared without their tracking tags.
- Links get `rel="noopener noreferrer"` and open in a new tab. An article's own anchors (`id`s, `#note` links) are kept with `article-` in front, so footnotes work and can't clash with nine turtles' page; the screen scrolls to them instead of opening a tab.
- Images are the one thing the browser may load from any address (the Content Security Policy's `img-src`), because articles show the publisher's own images. Scripts, styles, fonts and connections stay nine-turtles-only. The page's "no-referrer" rule means publishers aren't told an image was viewed in nine turtles.
- The one frame the browser may load is YouTube's privacy-enhanced player (`frame-src https://www.youtube-nocookie.com`), built by nine turtles itself, never from stored content, and only once the reader presses Play on a YouTube video. It is sandboxed and is told nine turtles' address (`strict-origin`), which YouTube's player needs to play (decision 0072).
- Authors are kept as names only: RSS's `address (Name)` form keeps just the name.

### Payments (decision 0094)

- **Off without** `NINE_TURTLES_DODO_API_KEY`, `_WEBHOOK_SECRET` and `_MONTHLY_PRODUCT` (all three or none; with them, `NINE_TURTLES_PUBLIC_URL` too). Test mode (`https://test.dodopayments.com`) unless `NINE_TURTLES_DODO_MODE=live`. `payments::Settings` never prints the key or secret.
- **Standing** (`payments::standing`): `Free` for the owner and `people.free` (everyone before structure change 18); else `Paid`/`OnHold` while `plans.access_until` is ahead; else `Trial` until `max(created_at, settings.payments_on_at) + trial_days`; else `Ended`. `Ended` refuses adding feeds (`feeds::add`, so the Add field and other apps; OPML import) with `402 {"error":"plan-ended"}`, and `checking::check` treats a feed with no current follower as away (`admin::AWAY_WAIT`).
- **Talking to Dodo:** a fresh reqwest client per request (20 s limit), `Authorization: Bearer`. `POST /checkouts` and `POST /customers/{id}/customer-portal/session?return_url=…`; `PATCH /subscriptions/{id}` `{"status":"cancelled"}` before `accounts::delete_me` deletes a reader (a failure answers `502 {"error":"plan"}` and deletes nothing).
- **Messages** at `POST /payments/dodo` (no cookie and no browser headers, so the same-site rule lets them through): Standard Webhooks signature (`payments::genuine`), five minutes' tolerance, ids kept 90 days in `payment_messages`. 401 for a bad signature, 200 for anything handled or ignored on purpose. Whose, stale messages and an earlier subscription's end: `payments::handle` (decision 0094). `access_until` rules: `payments::access_until`. A plan that starts calls `admin::due_again`.

### Newsletters (decision 0091)

- **Arriving:** nine turtles never receives mail itself. Cloudflare Email Routing hands each email for `in.nineturtles.app` to the Worker in `cloudflare/newsletter-worker/`, which posts it, raw and unchanged (`message/rfc822`), to `POST /newsletters/incoming` with `Authorization: Bearer <NINE_TURTLES_NEWSLETTER_SECRET>`. The secret is compared as a Blake2 hash, like the diagnostics key; at least 32 characters, or nine turtles won't start. Without it the route answers 404. Bodies over 10 MB (`EMAIL_SIZE_LIMIT`, the same in the Worker) are refused. The route sends no browser headers, so the same-site rule lets it through, and it uses no cookie.
- **Whose:** the Worker sends `X-Nine-Turtles-To` (the envelope recipient); only without it are the email's To, Cc, Delivered-To and X-Original-To tried (the sender writes those, so they never overrule the mail service). The part before `+` and `@` is looked up in `newsletter_addresses` (structure change 16): a current name is its reader's; a retired one (New address) answers 410; none 404. Names are `turtle-` plus 8 letters from the app-password alphabet (about 40 bits), made the first time the reader opens Settings (`GET /api/newsletters`); New address retires the current one; Undo (an hour) makes it current again. The domain shown is `NINE_TURTLES_NEWSLETTER_DOMAIN`, else `in.nineturtles.app`; any domain that reaches nine turtles is accepted.
- **Answers:** 200 kept, or dropped on purpose (`kept: false`): the reader unsubscribed from that sender less than 30 days ago (`STAYS_AWAY_FOR`; after that the feed is followed again), or it's a new sender and the reader follows `admin::MOST_FEEDS` feeds already; 404 no such address and 410 a retired one, both with `x-nine-turtles-answer: no-such-address` or `replaced` (the Worker bounces only answers with that mark, so a plain 404, when newsletters are off or `NINE_TURTLES_URL` is wrong, goes to `FORWARD_TO`); 429 after 200 emails or 5 MB of cleaned text in 24 hours for one reader (`DAILY_LIMIT`, `DAILY_BYTES`), or 100 MB for everyone (`ALL_DAILY_BYTES`), counted from the articles of newsletter feeds; 401 wrong secret; 413 too big; 422 not an email or no sender. The Worker passes anything else but 200 on to `FORWARD_TO` when set; otherwise it bounces a 4xx and throws on anything else so the sender's server tries again. `scripts/check-newsletter-worker.mjs` tests it with a pretend Cloudflare.
- **Reading** (`server/src/newsletter.rs`, mail-parser with `full_encoding` for Chinese and Japanese character sets): feed key `list:<List-Id>` or `from:<address>`, lowercased; fingerprint from the Message-ID through `feed::fingerprint`; title from the subject; date from `Date`; language from `Content-Language`; site from `List-Archive`; the one-click unsubscribe address is stored (see Telling senders below); the plain `List-Unsubscribe` page isn't.
- **Tidying before the safety cleaning:** the HTML is walked once and written out again without `<head>`, styles, forms, comments (Outlook's `<!--[if mso]>`), hidden elements (`display:none`, `visibility:hidden`, `mso-hide:all`, `opacity:0`, `max-height:0`, `hidden`), `cid:` and non-web images, images sized 0 or 1 pixel in their style, empty boxes and spacer cells, `<center>` and `<font>` (their contents kept), and the "View in browser" link (it becomes the article's link). A table is layout, and becomes a `<div>` per cell, when it is `role="presentation"`, holds another table, has a single column, or holds pictures or blocks; one with `<th>` headings is data and stays. `style`, `class`, `width`, `height`, `bgcolor`, `align` and `valign` go; `utm_…` and the other tracking query parts are taken off links. Then `feed::clean` does everything a feed article gets (tracking images by attribute, YouTube players, ammonia), so ammonia still has the last word.
- **Nothing is fetched to show a newsletter:** not its web version, not its images (the browser loads those like any article's). The only fetches are loading its tracking images once on arrival and its one-click unsubscribe, both below.
- **Never shared:** newsletter feeds and articles belong to one reader only (each copy carries personal unsubscribe tokens and addresses). A newsletter feed's `url` and `url_key` are `newsletter:<reader>:<sender key>` and its `newsletter_of` is the reader (structure change 16), so two readers on one list get two feeds; a newsletter is never the shared copy a web feed is.
- **Storing** (`newsletters::file`, one transaction): the sender's first email makes the feed (`next_check_at` the largest number, and `checking::DUE` and `checking::check` skip `newsletter_of`, so it's never fetched) and the reader's subscription; each email goes through `feeds::store_articles`, so entries, search and rules work as for any article. A newsletter feed nobody follows (`unsubscribed_at` set) drops its sender's emails; `folders::let_go` keeps a newsletter feed's line for that, and `people::delete` removes a deleted reader's newsletter feeds and addresses. OPML export leaves newsletter feeds out.
- **Labels** (structure change 17): the part after `+` (lowercase letters, digits, `.`, `_`, `-`, at most 64; anything else counts as no label) is recorded in `newsletter_labels` (name, label) when an email to it is kept, at most 100 per address (`MOST_LABELS`; anyone with the address can invent labels). `off_at` set (`POST /api/newsletters/labels` with `{label, on}`, the reader's current address only) makes mail to it answer 410 with `x-nine-turtles-answer: label-off`, which the Worker bounces. Labels cascade with their address.
- **Telling senders** (`newsletters::tell_senders`, started in the background by each round of background checking, after `folders::clear_unsubscribed`, so slow senders never hold up feed checks): `newsletter_senders` (structure change 17) keeps a newsletter feed's one-click address, from its first email with both `List-Unsubscribe-Post: List-Unsubscribe=One-Click` and an `https://` `List-Unsubscribe` (RFC 8058), exactly as written. Once the feed has no subscription waiting (`cleared = 0`) and `feeds.unsubscribed_at` is set, the row is claimed (`told_at`) and `List-Unsubscribe=One-Click` is posted to it once, through `fetch::post_form` (public addresses, time limit, no redirects). The address is never logged. A kept email clears `told_at`, since the reader follows the sender again. Nothing proves an email comes from the sender it names (DKIM isn't checked), so a forged email could name its own addresses: the first one-click address is kept rather than the newest, requests only reach public addresses with a fixed body, and the daily limits apply. Accepted for now; forged emails already arrive as articles.
- **Opened on arrival** (the owner's choice, decision 0091): for a new email (not one already stored), its tracking images, `<img>` with a width or height (attribute or style) of 1 pixel or less, at most `newsletter::MOST_OPENS` (3), are fetched once with `fetch::get` in a background task, under every rule for fetching feeds; the answer is thrown away and a failure is only logged.

### Imported stars (decision 0098)

- **Reading** (`server/src/star_import.rs`): `POST /api/starred/import` with the file as JSON, at most 25 MB (`SIZE_LIMIT`) and 10,000 articles (`MOST_STARS`, 413 past either; 400 `not-stars` if it isn't JSON with an `items` list or a plain list). Google Reader's shape (`alternate`/`canonical`, `origin.streamId` = `feed/<address>`, `published` in seconds, Feedly's milliseconds and `originId`), JSON Feed (with nine turtles' own `_nine_turtles` extension, whose `id` is `<feed address>#<fingerprint>`), and flat lists (`url`, `title`, `content`, RFC 3339 dates). An article with no `http(s)` link to its original isn't read. Text goes through `feed::clean` like any feed's.
- **Never shared:** an article already stored in the feed the file names (by fingerprint, else its exact link; never a newsletter feed) gets the reader's star. Any other is stored in a feed of the reader's own, `url_key` `imported:<reader>:feed:<normalized feed address>`, or `imported:<reader>:named:<feed name, lowercased>` when the file gives a name but no address, or `imported:<reader>:` when it names no feed (credited "Imported stars"); `url` is the real feed address (or `imported:` without one), so the starred export credits it and never shows the private key. No web feed's key can start `imported:<number>:` (`star_import::own_key`, with a test). So nothing one reader uploads appears in another reader's lists as the publisher's. That feed has `next_check_at` the largest number and `unsubscribed_at` set, so it's never fetched; `folders::let_go` and the yearly clean-up treat it like any feed nobody follows.
- **Hidden subscriptions:** the reader's entries need a subscription; one they don't have is made `unsubscribed_at` set and `cleared = 1`, exactly the state an unsubscribed feed with starred articles is in, so it shows in no list but Starred and search, and following the feed later works as ever. Entries are made `read = 1, starred = 1`; an entry the reader has keeps its read mark and gains the star. One transaction for the whole file; it never unstars or removes anything, so there's no Undo. No structure change.
- **Limits:** besides the file's 25 MB and 10,000 articles, a reader keeps at most `MOST_KEPT` (10,000) articles and `MOST_KEPT_BYTES` (50 MB of content and summary) in their `imported:` feeds, counted over that key range after the import's writes; past either the whole import is rolled back (409 `too-much`). An ended plan doesn't stop importing, as it doesn't stop starring.

### Data

- **Unsubscribing** deletes the reader's unstarred entries for the feed, their read history (their starred ones are kept), and, once nobody follows the feed, its articles nobody starred; the immediate undo brings them back, and after that only a restore from a backup does (see the floor).
- **The yearly clean-up** (`server/src/cleanup.rs`, structure change 15, decision 0089): unstarred articles older than one year, read or not, are deleted. Starred articles are kept forever. It works on each reader's entries first: every entry the reader hasn't starred whose article is over a year old goes, even if another reader starred the article (so what one reader sees never depends on another's stars); then every article over a year old that no reader has any more goes. It works 500 at a time, each in its own short transaction, so readers are never kept waiting.
- An article's age counts from when nine turtles **first received it**, not its published date, so old posts from a newly added blog aren't deleted the next night.
- nine turtles remembers the fingerprint of each deleted article in `forgotten_articles` (a short line of text, about 100 bytes: some 10 MB a year at 100,000 removed articles a year), so an article still listed in its feed isn't stored again as new (`feeds::store_articles` skips it). These records are removed when nobody follows the feed any more (`folders::let_go`). Article numbers freed by the clean-up are never given again (`articles_high_water`). Because these records are the feed's, shared by its readers, someone who starts following a feed others already follow doesn't get the removed posts the publisher still lists (they were received over a year ago); someone adding a feed nobody follows gets all its listed posts, as new arrivals.
- Unsubscribing from a feed keeps its starred articles.
- This clean-up runs only right after a nightly backup has been stored successfully (`backup::run`), so everything it deletes is in that night's copy; while backups fail it waits, and the failed backup shows in `/status`'s recent problems. Without backup settings it never runs. It says what it removed in the server log. Deleted articles remain recoverable from backups for as long as backups are kept (the monthly copies, a year).
- **Search:** FTS5 configured so words in scripts with combining marks (such as Hindi's vowel signs) are not split apart; covered by tests with Hindi text. The search table is "contentless" (words and positions only, no copy of the text) and holds each article's title and tag-free text under the article's number; articles enter it as they arrive or change, leave it by a database rule when deleted, and older ones are added once in the background after the first start (structure change 6, decision 0023). Because it keeps no text, FTS5's `snippet()` can't cut excerpts from it; each search result's one-line excerpt is cut in Rust from the stored article for the 50 results on the page, and sent as plain-text pieces marked as matches or not, never as HTML (decision 0035).
- **Read and starred** are two yes/no marks on each reader's entry for an article (`entries`, structure change 12), with small "partial" indexes for the Unread and Starred views and the unread counts (decision 0018). An entry also copies its article's feed and place in the list, so each list reads one index of the reader's own entries, already in order (`tests/speed.rs`).
- **"Mark all as read"** receives the exact list of items on screen, so items fetched in the background are never touched. It is undoable: undo sends the opposite mark for the same items.
- **"Catch me up"** is the one exception, asked for in so many words: it marks every unread article in Unread from before the start of the reader's day (their device's midnight, never later than the server's now) and answers their numbers, so Undo sends the opposite mark for exactly those. **Letting unread go** (Settings › Reading) marks the reader's unread articles older than their chosen wait as read in each background round, once the choice has stood a minute (`let_go_at`), so arrow keys passing a shorter wait mark nothing. Both read only the reader's unread entries through an index (tests/speed.rs checks this). Decision 0097. **Marking older, above or below as read** (decision 0103) is the second: when part of the list on that side isn't loaded yet, the screen sends the list (as `GET /api/articles` names it), the chosen article's place (date and number), the side, and the list's `latest`; the server marks the reader's unread entries in that list past that place, with an article number no higher than `latest` (so nothing that arrived since is touched), and answers their numbers, so Undo sends the opposite mark for exactly those. Search results, which the server can't name as one list, are fetched page by page and marked by name; a search's answer carries its own `latest`, and no article numbered above it is marked.
- **Saving marks** happens behind the screen, one save after another in the order made. A save that can't reach nine turtles (no connection, a timeout, or 502/503/504 while it restarts for a new version) tries again for up to a minute from when the mark was made; any other answer fails at once. Lists don't wait for a save that's waiting to try again (decision 0073). With no connection at all, a mark waits on the device (IndexedDB) and is sent once one is back (SPEC section 32).
- **The latest mark wins** (decision 0101): each entry remembers when its read mark and its star were last set (`read_marked_at`, `starred_marked_at`, milliseconds by the server's clock, structure change 21). Every mark says when it was made (`at`; the app corrects its device's clock by the server's Date header), the server never takes a time later than its own now, and a mark older than the stored one changes nothing, so a mark sent late from a device that was offline never undoes a later one. Marks from other apps, Catch me up and letting unread go count as made when they happen.
- **Readers** (decision 0086): a `people` table, where reader 1 is the owner. Each feed and its articles are stored once and fetched once, however many readers follow it; everything personal carries the reader's number (`person_id`), and every request reads and changes only the signed-in reader's lines (tested in `server/tests/walls.rs`). Structure change 11 did this for devices, settings, app passwords, folders, saved searches and rules; structure change 12 for following feeds (`subscriptions`: the reader's name for each feed, when they followed and unsubscribed, and the feed's own settings) and the read, starred and muted marks (`entries`). Both made everything already stored reader 1's. Following a feed someone already follows stores no second copy: the reader gets a subscription and entries for its stored articles (those the publisher still lists unread, older ones read; from OPML, all read). `feeds.unsubscribed_at` (null while anyone follows) and `feeds.check_at_most` (the shortest any follower allows) are worked out from the subscriptions by `feeds::refresh_shared` whenever one changes, so background checks and WebSub read only `feeds`. Database rules refuse to delete an article a reader still has, or a subscription that still has entries.
- **Pausing a feed** (decision 0095, structure change 19): `subscriptions.paused_at`, the reader's own. `feeds::store_articles` gives a paused reader's new entries `read = 1`, so nothing reaches Unread; checking and WebSub carry on as usual. Unpausing (`folders::set_paused`) sets `read = 0` on the newest `folders::BACK_FROM_PAUSE` (3) unmuted entries whose article was received since `paused_at`, then runs the reader's rules on them again. A move ("Find new address") carries `paused_at` over; following again clears it.
- **Folders** are a `folders` table and a `feed_folders` list of (folder, feed) pairs, so a feed can be in several and deleting a folder never touches feeds (structure change 5, decision 0020). Each folder is a reader's, and one reader's folder names are unique whatever their capitals (structure change 11, decision 0086).
- **Unsubscribing hides first, clears later:** the reader's subscription is marked `unsubscribed_at` and the feed leaves their lists at once (and the background checks, once nobody follows it); ten minutes later, or when that reader unsubscribes from another feed, their unstarred entries and folder pairs for it are deleted. Their subscription stays (marked `cleared`) only while their starred articles need its name. Following it again reuses the line. Other readers of the feed keep everything. When nobody follows or waits on the feed any more, its articles nobody has are deleted, then its hub subscription, and the feed's line once no article is left. New articles are numbered above the highest number ever given, so numbers freed by clearing are never reused (decision 0020).
- **Rules and mutes:** a `rules` table, and a `muted` mark on each reader's entry that is always set together with `read`, so unread counts, the Unread view and other apps need nothing new; All, feed and folder lists leave muted articles out, search and Starred keep them. Each rule is a reader's, and each reader's rules run inside `store_articles` on the articles it just numbered, changing only that reader's entries (decision 0086); a rule's feed or folder going clears its place and marks it `place_gone` rather than deleting it (structure change 10, decision 0077).
- **At most 1,000 feeds per reader** (`admin::MOST_FEEDS`, decision 0090), the owner too: counted from the reader's followed subscriptions inside the same write that adds one (`feeds::follow`), and asked before anything is fetched (`feeds::add`), so a full reader's address costs no publisher a request; the Add field, the welcome's starter feeds and other apps (`quick_add`) all go through it and get `409 too-many`. An OPML import that would end above 1,000 is rolled back whole (`409` with `following`, `adding` and `most`). Undo for unsubscribing and "Find new address" (a move) aren't limited.
- **OPML import** writes the feeds and folders down in one transaction and fetches nothing; background checking fetches the new feeds in its usual rounds.
- **Edited articles:** when a publisher edits an article already stored, its title, link, author, text and language are updated; its place in the list, read mark and star are kept (decision 0019).
- **Background checks** keep each feed's schedule and failure history in a few columns on `feeds` (structure change 4). The screen learns about new articles by asking, once a minute, whether any article numbered above the newest it loaded belongs to its list (decision 0019).
- **Each feed's own settings** (decision 0082) are columns on each reader's subscription (structure change 9 put them on `feeds`; structure change 12 made them each reader's): `river` (it skips Unread and counts nothing: the Unread list and its "new items" question leave it out, and the sidebar's count for it is 0), `check_at_most` (seconds; the feed is checked as often as its most eager follower allows), `open_on_site` and `paused_at` (see "Pausing a feed" above). Edit feed's save leaves any it doesn't name as they are, so an older open tab can't reset them; following a feed again resets them.
- **Saved searches** are a small `saved_searches` table: a name (unique for each reader, decision 0086) and the search field's own description of the search, as JSON, which the server only checks is a small JSON object (structure change 8, decision 0081). Deleting one removes only that row; Undo saves it again. When a folder is deleted or an unsubscribed feed is cleared, the reader's saved searches limited to it are pointed at number 0 (nothing), since SQLite may reuse the number.
- **Settings shared across devices** (the sort order and the reading mode, decision 0068) live in a small `person_settings` table, one row per reader and setting (decision 0086); `settings` keeps only what belongs to nine turtles itself (`articles_high_water`, and the sign-up switch, decision 0087); a save names only the settings it changes; per-device reader controls stay in the browser. The reader's own keys (decision 0110) are one more row, `keys`: JSON of only the changed keys by stable binding names, saved whole; the server checks only their size and shape, and the browser decides what they mean (`web/src/lib/keyboard.ts` `resolve`), keeping a copy in local storage for the first press and offline.
- **Exports:** OPML for feeds and folders; starred articles as a JSON Feed 1.1 file, each item carrying the feed it came from in a `_nine_turtles` extension (`_slowfeed` before the rename) (decision 0024).

### Sign-in and security

- **Sign-in by email and password** (decision 0087). `people` has an `email` (unique however it's capitalised: `COLLATE NOCASE` and a unique index) and a `password_hash` (structure change 13). Passwords are stored only as a slow, salted hash (argon2id, `password.rs`). The owner (reader 1) keeps their password-only sign-in: no email means the owner, checked against `NINE_TURTLES_PASSWORD_HASH`, made by `nine-turtles set-password` and given to nine turtles as a setting. The owner can also sign in with their own email, against the same setting unless they have a `password_hash` of their own. An unknown email (or a reader with no password) is checked against a scramble nobody chose a password for, so the answer and the time taken are the same as for a wrong password. Every check runs off the async threads (`spawn_blocking`). The wrong-try counts (`state.limiter`, one count per email, the owner's email included, and one for the owner's password-only sign-in, so the owner has two separate sets of five tries; accepted so a stranger can't tell which email is the owner's) are locked only to check and record a try, never during the check; a try counts as wrong from the start and is forgotten if right, so tries sent together can't race past the limit. At most two checks run at once for every sign-in by email (the owner's email too, so its timing gives nothing away), and one for the owner's password-only sign-in on a line of its own (`state.password_checks`, tokio semaphores), so a flood of guesses can't use up memory (each check takes about 19 MB) or hold up the owner's password-only sign-in. A password over `password::MAXIMUM_LENGTH` (1,024 bytes) is answered "wrong password" at once, before it's counted or queued.
- **Sign-up** (decision 0087): one app-wide switch in `settings` (`sign_up`: absent means Closed, or `invite`), with the invite link's ticket kept only as a BLAKE2s scramble (`sign_up_invite`, and `sign_up_invite_made_at`). The ticket is 32 random bytes, as for a device's sign-in. Open is refused by the server unless nine turtles can send email (decision 0088); while Open, signing up makes no account, only an emailed link (below), and the account is made when it's followed. Sign-up tries are capped at 20 in any hour for the whole app: every try that reaches the password scramble counts, a taken email too (kept in memory, `state.sign_ups`), an Open sign-up's try included, alongside the accounts made in the hour (from `people.created_at`, so a restart doesn't reopen it; checked again inside the same `INSERT`). Sign-ups go one at a time: `state.sign_ups` is a lock held while the password is scrambled and the account made, and also while an Open sign-up's link is followed and its account made (within the same 20-an-hour count of accounts). The invite ticket travels in the address's fragment (`/sign-up#invite=…`), never seen by a server, and reaches the server only in the POST body. New readers' passwords: at least 12 characters (the same as `nine-turtles set-password`), at most 1024 bytes. Only the owner (`people.owner = 1`) may read the readers list (`GET /api/people`: number, email, owner or not, joined; nothing about reading), set their email, or change sign-up; anyone else gets 403. The owner's Readers page (`GET /api/admin`, decision 0090) is owner-only the same way: app-wide counts, the database's size, whether backups and email are on, the problems logged since start (as on the diagnostics page), and for each reader their email, joined, how many feeds they follow and how many of those keep failing. Counts only: never which feeds, nothing about reading, and not their last-here day (it waits for the owner's answer, `docs/planning/questions.md`).
- **Email** (decision 0088): plain SMTP with `lettre` (`email.rs`), STARTTLS on 587 (or encrypted from the start on 465), refused unencrypted except to the same computer; five `NINE_TURTLES_SMTP_*` settings, all or nothing (the port alone counts as some), and no email at all without them; set without `NINE_TURTLES_PUBLIC_URL`, nine turtles refuses to start. `email::Settings` hides the SMTP password from any debugging print, and a failed send is logged in nine turtles' own words, never the mail server's (which often repeat the address). Only a bare address is accepted anywhere an email is typed (`people::plausible_email`: no name, `<` `>`, quotes, commas, semicolons, colons, brackets, backslashes, spaces or control characters, and lettre's own parse must equal the text), and each email goes to a `Mailbox` built from that parsed address, so `name<someone@example.com>` can't dodge the per-address count. Emails are short plain text, sent behind the answer so timing never says whether one went out; links start with `NINE_TURTLES_PUBLIC_URL`, never a request's address. Tests swap SMTP for an in-memory outbox (`Mailer::outbox`); the browser tests use a made-up mail server on the same computer.
- **Emailed links** (`accounts.rs`, structure change 14): an `email_links` table, each link a 32-byte random ticket kept only as a BLAKE2s scramble, used once (`UPDATE … SET used = 1 … RETURNING`, so two presses can't both use it), 24 hours to confirm an address, 1 hour for a new password and 15 minutes to sign in. The ticket travels in the address's fragment (`/reset-password#ticket=…`, `/confirm-email#ticket=…`, `/sign-in-link#ticket=…`), as the invite does: never seen by a server or its logs, read by the page and sent in the POST body. At most three links to one address in any hour, whatever for, and one link of each kind (password, sign-in, change of email) a minute (`EMAIL_GAP`, so a second press of Send link sends nothing; sign-up links aren't held to it, so a corrected password's link is saved; decision 0092), and at most three tries to change one reader's email: counted and saved in one `BEGIN IMMEDIATE` transaction (`accounts::make_link`), so requests sent together can't race past either count. A try to change to an address another reader has (or one past its hour's emails) is saved as a spent line with `emailed = 0`: it counts towards the reader's three but never the address's, so neither the answer nor the database work says the address is taken. An Open sign-up's email and argon2id password wait in the link; the password is scrambled whether or not the address already has an account, so the time taken doesn't tell; the account is made, within the 20-an-hour cap, when it's confirmed, and the waiting scrambles for that address are blanked then. Expired links are deleted with every new link and every round of background checking (`accounts::tidy_links`), but only once they're also an hour old, so a sign-in link that stopped working after 15 minutes still counts towards its address's three. "Forgot your password?" and "Email me a sign-in link" always answer the same, after the same database work for an unknown address (`make_no_link`). A new password signs out every device of that reader, deletes their app password and spends their unused sign-in links.
- **Sign-in links** (decision 0096, structure change 20, which made `email_links` again to allow the purpose `sign-in`, copying every line): `POST /api/sign-in/link` (`{email}`, answered 202 whoever asks) and `POST /api/sign-in/link/use` (`{ticket}`). Using one is a single `UPDATE … RETURNING` that also needs the reader to still have the address the link went to (`people.email = email_links.email`), so a changed email leaves earlier links behind; it then signs the device in as a password would (`remember_device`). It bypasses the count of wrong passwords, as the link itself is the proof; the hourly and per-minute email limits are its only limits.
- **Passkeys** (decision 0109, `passkeys.rs`, structure change 25): WebAuthn, checked by webauthn-rs 0.5 (with its `conditional-ui` part). The relying party is `NINE_TURTLES_PUBLIC_URL`'s exact origin, its host the relying party ID; without it, `http://localhost` on any port; a numeric host turns passkeys off. `GET /api/session` says which (`passkeys`: the origin or null), and the page offers passkeys only at that origin in a browser with `PublicKeyCredential`. Adding: `POST /api/passkeys/add` (`{password}`, checked by `auth::ask_password` under the reader's sign-in account, as changing email is) answers a challenge for a discoverable passkey with user verification required (`residentKey: required`, the reader's other passkeys excluded); `POST /api/passkeys/add/finish` checks the device's answer and stores the `Passkey` as JSON with its credential number (`UNIQUE`, so one passkey can't be two readers') and the reader's random user handle (a UUID, the same for all their passkeys). Signing in: `POST /api/sign-in/passkey` answers a discoverable challenge (no allowed list; the page picks the browser's sheet or the email field's autofill); `POST /api/sign-in/passkey/finish` finds the passkey by its credential number among those not removed, requires its stored handle to match the one the passkey returns, lets the library check the signature, user verification and counter (a counter that goes backwards is refused), saves the updated counter and `last_used_at`, then `remember_device`, exactly as a password sign-in. Challenges (`passkeys::Ceremonies`) live in memory under a 32-byte random ticket, five minutes, taken out on the first answer whatever it is, at most 1,000 at once (expired ones go first, then `429 wait`), one adding challenge per reader, and an adding challenge finishes only for the reader who asked. No wrong-try waits: a passkey can't be guessed, and a refused one must never lock the password out; refusals are logged as information. Rename, remove and Undo (`/api/passkeys/{id}/name`, `/remove`, `/undo`) touch only the signed-in reader's lines; removing sets `removed_at` (no longer signs in), Undo clears it within `passkeys::UNDO_FOR` (10 minutes), and older removed lines are deleted when the reader next lists, adds or removes. At most 20 per reader. `passkeys` is in `PER_READER_TABLES`. webauthn-rs links the system's OpenSSL (the Dockerfile installs `libssl-dev` to build and `libssl3t64` to run).
- **The owner's password set by email, and the way back** (decision 0088): a password the owner sets with a link goes in `people.password_hash` and wins over `NINE_TURTLES_PASSWORD_HASH`, but only while that setting stays as it was: the reset saves a BLAKE2s fingerprint of the setting in force (`settings.owner_password_from`, never the line itself), and on every start `auth::owner_password_follows_setting` compares it. If the setting is a real line and its fingerprint differs, the owner's own password is cleared, the fingerprint deleted, every device signed in as the owner signed out and their unused password and sign-in links spent, so the new setting is the owner's password again (`docs/operations/owner-password.md`). A missing or invalid setting changes nothing. The owner's "Your email" box asks for their current password, checked as their password-only sign-in checks it (`auth::ask_password`: the same count of wrong tries and the same line). Changing email needs the reader's password, checked as sign-in checks it: the same count of wrong tries (under the reader's email, as a sign-in by email is counted) and the same bounded line of checks for sign-ins by email (`state.password_checks`); it then sends the link to the new address, and tells the old one once it's done. A new password from a link is scrambled only once its ticket is found good, waiting its turn in that same line, so made-up tickets cost the server nothing.
- **Deleting an account** (`people::delete`): one transaction that first lets go of each feed the reader follows as unsubscribing does (`folders::clear`, their stars included), so a feed nobody else follows stops being checked and its articles nobody has go, then deletes every `email_links` line to the reader's email (an Open sign-up's has no `person_id`), then empties `PER_READER_TABLES`, which names every table with a `person_id` column; `server/tests/accounts.rs` reads the tables from `sqlite_master` and fails if one is missing, still holds the reader's lines, or lost any of the owner's, or if `email_links` still holds the reader's email. Never the owner. No password is asked for: the owner's choice (decision 0088).
- Long-lived session cookie per device, each device belonging to one reader (decision 0086) (secure, HTTP-only, SameSite=Strict): a random ticket, of which the database keeps only a scrambled copy. A year from last use. Plus protection against other websites submitting actions on the owner's behalf ("cross-site request forgery"): actions must come from nine turtles' own pages.
- A strict Content Security Policy (a browser rule): the browser refuses any script that doesn't come from nine turtles itself. This is a second layer behind sanitizing.
- Failed sign-in attempts are rate-limited for each account on its own (each email in small letters, plus one count for the owner's password-only sign-in), wherever they come from: five free tries, then a doubling wait up to an hour. At most 4,096 accounts' counts are kept in memory; when full, what would be forgotten anyway goes first, then the quietest account that isn't waiting. Sign-in tries are still decided one at a time, which also slows anyone trying to push a waiting account out by guessing thousands of others.
- Secrets (password hash, diagnostics key, backup storage key, SMTP key) come from environment variables, listed in `docs/operations/settings.md`.
- **Other apps** (Reeder, NetNewsWire) sync through the Google Reader API at `/api/greader` with an **app password**, never the owner's own: 24 random letters and digits (about 119 bits) made in Settings by a signed-in page, shown once, kept only as a BLAKE2s scramble in the `app_passwords` table, one per reader; the scramble is unique, so an app password says whose it is (decision 0086) (it can't be guessed, so a fast scramble is enough, as for session tickets), sent by apps in an `Authorization` header that no other website can add. Wrong app passwords aren't slowed down, so a stranger can't lock the owner out, but are counted on the diagnostics page. Making a new one or turning it off signs every app out. Details: `docs/decisions/0070-other-apps.md`.
- **AI assistants (MCP)** connect at `/mcp` (`server/src/mcp.rs`): JSON-RPC over "Streamable HTTP", each POST answered with JSON, no streaming and no session kept. They sign in with OAuth 2.1 (`server/src/assistants.rs`): metadata at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`, dynamic registration at `/oauth/register`, the reader's approval on `/oauth/authorize` (a page of the app), PKCE S256 only, codes (10 minutes) and tickets (access 1 hour, refresh 90 days and rotated) kept only as BLAKE2s scrambles in `assistant_codes` and `assistant_tokens`; or with an assistant key (`nt_` and 64 hex characters, no expiry, a `key` ticket). Each `assistant_connections` line is one reader's and Disconnect deletes it with its tickets. `/mcp`, `/oauth/token` and `/oauth/register` skip the same-site check (no cookie is used there). Per reader: 60 calls a minute, 3,000 a day, 20 feeds added an hour, counted in memory (`assistants::Limits`). A feed an assistant unsubscribes from gets `subscriptions.kept_until` 30 days on, which `folders::clear_unsubscribed` respects. No library: see `docs/decisions/0111-assistants-mcp.md`.
- The website's feed finder (`/api/find-feeds`, decision 0099) is the one other thing anyone may use without signing in; browsers let only nineturtles.app's pages read its answers (CORS; a program can still ask directly, which its limits cover), and it never touches the database.
- A public status page (`/status`) says only that nine turtles runs and its version; a diagnostics page (`/diagnostics`) needs a read-only key and never shows the reader's feeds or articles.
- Details and rejected alternatives: `docs/decisions/0010-sign-in.md`, `docs/decisions/0087-sign-in-by-email.md`, `docs/decisions/0088-account-emails.md` and `docs/decisions/0109-passkey-sign-in.md`.

## Part 4: Automatic checks

Wherever a principle can be checked by a computer, it is. These run on every pull request, all through `scripts/check.sh`, in parts side by side (decision 0065; what each step does: `docs/operations/checks.md`). A pull request that changes only documents skips all but the quick ones:

| Principle | Check |
|---|---|
| The computer checks the work | Rust: format, lint and tests. Frontend: type check and tests. Every pull request except documents-only changes and tiny fixes also gets a second-agent review. |
| Owner can see the change | Screenshots of every screen in Original, by day and by night (the other themes on the list, article, Settings and Edit feed screens), at desktop and phone width, attached to each pull request |
| Libraries stay safe | A weekly report of known security problems in our libraries. It only reports; nothing is updated automatically. |
| First floor (accessibility) | Automated accessibility and contrast tests on every screen, in every theme by day and by night |
| No motion (DESIGN.md) | Fails if animations or transitions appear in the styles |
| Fast by design | Fails if the frontend download grows past its size budget |
| Never add a library without asking | Fails if the code uses a library that isn't on the approved list in `docs/libraries.md`. Agents add to that list only after the owner has said yes. |
| Publisher floor | Tests confirm conditional requests, backoff and that no article pages are fetched |
| Search for Hindi | Tests search Hindi text and find the right results |
| Data floor | Database changes are tested against a copy of real-shaped data |
| Fast at real size | Speed tests run against a made-up database the size of 500 feeds and a year of articles |
| Keyboard floor | Every feature has tests that use it with the keyboard only |
