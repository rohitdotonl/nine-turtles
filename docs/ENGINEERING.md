## Part 2: Engineering principles

Same structure as `DESIGN.md`: a floor that nothing can trade away, then ranked principles. **When two principles conflict, the higher one wins.**

### The floor: never lose the reader's data, never put the reader at risk

- Every change to the database's structure is tested on a copy before it runs for real, and is backed up first: nine turtles stores a copy before changing its structure, and doesn't change it if that copy fails (decision 0076).
- Nothing deletes data without undo. Backups are taken nightly and before every structure change, not before each deletion: unsubscribing deletes the reader's read history for the feed and their unstarred articles of it (the articles themselves once nobody follows the feed and nobody starred them), which the immediate undo brings back; after that, what was there at the last nightly copy can still be restored from the backups (nightly copies for 30 days, monthly ones for a year). Anything added since the last copy isn't in them. The owner accepted this (23 October 2026; the backups arrived 25 October, decision 0076). Deleting one's own account (decision 0088) is the second exception the owner chose: one "Are you sure?", the reader's downloads offered first, then deleted at once with no undo; the nightly backups still hold it. Deleting one's data while keeping the account (decision 0117) works the same way, for the owner too. The yearly clean-up (decision 0089) is the third, agreed with the owner as part of the plan for many readers: unstarred articles over a year old are removed with no undo, only just after that night's copy is stored, so the backups hold them (the monthly copies for a year). Articles the reader highlighted or wrote a note on are kept like starred ones, by unsubscribing and the clean-up alike (decision 0164). Unsubscribing asks first when anything is kept there; "Remove them too" deletes the starred and marked articles and the note on the person too, done only when the unsubscribe is cleared (so the immediate undo still brings everything back), with the backups behind it as for any unsubscribe (the owner, 3 November 2026).
- Any change that could lose the reader's data (a structure change that drops or rewrites data, for example) is still raised with the owner first.
- Article content from feeds is always sanitized before display.
- Passwords and secrets never appear in the code or in GitHub.

**Test:** If this goes wrong at the worst moment, can everything be recovered?

### 1. The computer checks the work

The owner doesn't review code line by line, so automated checks do the reviewing. Every change must pass the compiler, the tests and the automated checks before it counts. A feature isn't done until it has tests.

**Test:** If an agent broke this tomorrow, would something fail automatically?

### 2. Boring and few

Prefer well-known, mature tools, and as few of them as possible. Every new library or service needs a reason, because each one is something that can break, change or disappear.

**Test:** Can this be done with what we already have?

Small things a library would usually do are written once, in one place, rather than added as a library. Use these instead of writing another copy:

- Server: the folder and rule actions every door shares in `server/src/folders/shared.rs` and `server/src/rules/shared.rs`; hex, base64 and web forms in `server/src/encoding.rs`; calendar dates and RFC 3339 times in `server/src/dates.rs`.
- Web app: talking to the server (`isRecord`, `getJson`, `sendChange`) in `web/src/lib/http.ts`; small settings kept on the device (local storage, which a private window may refuse) in `web/src/lib/device.ts`; what the reader typed and hasn't saved (notes, Edit, Edit folder, Add), kept under a name for each reader until it's saved, cancelled or discarded, never on a timer and never sent until saved, in `drafts.ts` (decision 0235); saving marks and settings in order, and keeping only the newest answer, in `saving.ts` and `inorder.ts`; the messages said in many places ("Undone.", nine turtles can't be reached) in `messages.ts` (BRAND.md → "Messages").

Where the web app's code lives, one job per file in `web/src/lib/`:

- **Feeds and articles:** what the server's answers look like (`shapes.ts`), the feeds and folders (`feeds.ts`), the article lists (`lists.ts`), whole articles kept close at hand (`articles.ts`), the reading settings (`reading.ts`), importing (`importing.ts`) and times in words (`times.ts`).
- **The signed-in screen** (`Shell.svelte`) holds the pieces together. Each piece below is made once per signed-in screen, never shared between readers:
  - the reader's feeds and folders, how they load and how each is removed with Undo: `library.svelte.ts`;
  - the reading settings as the screen shows and saves them: `reading-settings.svelte.ts` (not `settings.svelte.ts`, which a Mac would mistake for `Settings.svelte`);
  - when each keyboard shortcut applies to what's on screen: `shortcuts.ts` (`keyboard.ts` still decides which shortcut a key press is); stepping through articles and feeds (j and k, Home and End, Shift+J and Shift+K, and where the keyboard's place follows): `moving.ts`; where the keyboard's place lands on arriving somewhere (a page's heading, the add field, a sheet's or the welcome's heading, or back on the Settings row that opened a page): `landing.ts`;
  - moving between places (which open as a sheet over another, what a move keeps, where the keyboard goes back to when a sheet closes, and `Steps`: the step each move adds to the browser's history and the steps back): `navigation.ts`;
  - the screen's arrangement (width step, which areas show, the sidebar and list toggles and their dragged widths): `layout.svelte.ts`;
  - when the copies for reading offline are brought up to date: `Keeper` in `offline.ts`;
  - the search the screen holds (the field, the results, the phone's Search field, what "Save search" saves): `searching.svelte.ts` (`search.ts` still reads and words a search);
  - which rows the article list's More (…) menu has and what each does: `listMenu.ts`; what the list says when it has nothing to show (a place you don't have, a list that couldn't load, an empty list): `listWording.ts`; what its heading says (the place's own name, "Folder not found", or "Results in …"): `listHeading.ts` (the tab's title and the phone's Back button use the same name); its title line (the name, with Search on a phone and the More menu beside it) is drawn by `ListHead.svelte`;
  - where the first visit's welcome shows (instead of the list, taking the list's room beside the reading area, alone on a phone) and when "New to feeds?" gives way to home: `firstVisit.ts`; the welcome itself is drawn by `Welcome.svelte`;
  - the sidebar's fixed lists (Unread, Starred, Notes and All articles): `SidebarViews.svelte`; its foot (+ Add, Keys, Settings): `SidebarFoot.svelte`; a person's or publication's page, its Edit and a source's settings: `WhoPage.svelte`, `WhoEdit.svelte` and `SourcePage.svelte` (a source's own rows, shared by Edit for one source and the source's page, in `SourceFields.svelte`).
- **Drawn once:** the folder edit sheet is one `editor` snippet in Shell, used for both the sheet and the phone's page; + Add and "New to feeds?" are one `task` snippet. A change to them is made once.

### 3. No vendor lock-in

nine turtles must be able to move to any host in an afternoon.
- It runs as one ordinary program plus one SQLite file. No host-specific databases, queues or functions.
- All settings come from environment variables, never from a host's dashboard alone. Their names and meanings (never their values) are listed in `docs/operations/settings.md`.
- Backups are ordinary SQLite files and go to any S3-compatible storage, chosen through settings alone; nine turtles speaks S3 itself, with no storage company's library (decision 0076).
- Moving hosts is a written, tested procedure (`docs/operations/moving-hosts.md`), not a hope. The reader's own OPML and starred exports mean they can always leave too.
- All automatic checks run through one script in the repository. GitHub Actions only calls that script, so any other CI service, an agent or a person can run exactly the same checks.
- The same rule applies to libraries: prefer standard, replaceable choices.
- The same rule applies to AI agents: instructions live in the repository as plain documents (`AGENTS.md`, `docs/operations/`), not only inside one agent tool's settings, so the owner can switch tools.

**Test:** Could nine turtles move to another host in an afternoon?

### 4. Fast by design

The engineering side of "slow app, fast interface." Speed is a requirement with numbers attached:
- Interface actions under ~100 ms.
- A small page download, with a size budget checked automatically: at most 200 KB (compressed) of app code and styles on first visit (raised from 150 KB by the owner, 2 November 2026, decision 0136), and at most 400 KB of fonts (only the alphabets nine turtles needs, cached after the first visit). The reading faces for Devanagari and Arabic (decision 0227) are downloaded only by readers of those scripts, so each has its own budget instead, at most 150 KB. The build leaves notes for the next agent out of the files it copies from `web/public/` (the service worker, the page, the manifest and the icon), so they don't count against it (`web/vite.config.ts`).
- No database query that searches without an index.

**Test:** Is the speed checked automatically, or are we hoping?

### 5. Fail small, fail visibly

One broken feed never affects others. One failed step never crashes the app. If nine turtles stops answering, GitHub emails the owner within about 15 minutes (the health check). When something fails, the owner can see it in the daily check or in the logs (and at the top of Settings › Everyone you follow), in plain words; the reader is never shown a technical error.

**Test:** What's the smallest thing this failure can take down?

### 6. Built to last ten years

No trendy tools that might be abandoned. Updates happen on purpose, not automatically. Everything needed to rebuild the app lives in the repository.

**Test:** Could someone rebuild and run this in 2036 from the repository alone?

### 7. Written for the next agent

Every agent session starts with no memory. Code, docs and decision records explain *why*, not just *what*, so the next agent doesn't undo a deliberate choice. Significant decisions get a short note in `docs/decisions/`.

**Test:** Would a fresh agent understand why this was done, without asking?

### Keeping the code tidy

What the code tidy-up of October 2026 learned (its check is decision 0126). The code had grown hard to work on in ways each change made a little worse, because an agent can't see what it can't read.

**Before writing code, ask in this order, and stop at the first yes** (decision 0127, after Ponytail's ladder). These are about the code, not the feature: what to build is settled by `docs/SPEC.md` and the owner, and if you think a feature shouldn't exist, ask.

1. Could the change work without this new code at all? The best code is code nobody has to write or keep.
2. Is it already in this codebase (see "Look before you write" below)?
3. Does Rust's standard library, SQLite or the browser already do it?
4. Does a library we already have do it (`docs/libraries.md`)? Adding a new one needs the owner's yes.
5. Can it be a line or two in an existing place?
6. If every answer is no, write the smallest thing that works, with its tests (a feature always has tests).

Never cut the floors to write less: sanitizing, security, accessibility, undo and backups stay whole.

The lessons:

- **Keep files small, one concept each.** Giant files were the root of most of the mess: `Shell.svelte` reached 2,261 lines, and an agent that can't read a whole file adds a new copy of something instead of finding the old one. Files have a size limit, not counting tests, and a few older, longer files may only shrink ("Code stays tidy" in `docs/operations/checks.md` says how much). When a file nears the limit, first split it by concept, as its own pull request that only moves code (tests move with it), then make the change.
- **Look before you write.** Search for an existing helper first ("Boring and few" above lists the shared ones). The survey found six copies of hex encoding, four of the calendar-date sum and thirteen of `isRecord`, each slightly different.
- **One action, one place.** The web app and the AI assistants (MCP) do the same things for a reader, so new code makes them call the same functions (as `folders::delete`, `folders::rename`, `rules::delete`, `marks::set` and `feeds::from_entries!` are), never a copy of the SQL of their own. Copies drift: the sync API for other apps (removed in decision 0184) once sent tracking pixels the web app removed. One kept apart on purpose: the screen's Mark all as read marks the rows listed, and an assistant's `mark_feed_read` (`marks::whole_feed`) a whole place.
- **Draw a screen once.** The phone and the computer share one snippet or component; a screen written twice gets fixed in one place only.
- **Delete what you replace, in the same change.** A replaced feature, an old name or an old way of signing in doesn't stay "for a while" without a date: the old-name shims and the owner-password leftovers outlived their reason by weeks (decisions 0124, 0125). Nothing unused stays; the check fails on it.
- **Answers can arrive out of order.** Two saves or loads in flight can come back in either order; use `saving.ts` and `inorder.ts` rather than trusting the last answer.
- **Never name two files the same but for capitals** (`settings.svelte.ts` beside `Settings.svelte`): a Mac's disk can't tell them apart, and the build broke there while Linux checks passed.
- **Splitting costs a little download.** A new Svelte component costs about 250 bytes, and the download has a 200 KB budget; prefer a plain `.ts` file for logic, and moves that also delete code.
- **A test that fails now and then is fixed at once**, never retried until it passes (decision 0114): flaky tests cost every later pull request a slow re-run.

## Part 3: Technical decisions

These were decided with the owner. Changing any of them needs the owner's approval. Library versions and maintenance status should be checked when work starts.

### Stack

**Backend: Rust**, chosen because it compiles to a single small program, uses little memory, and its strict compiler catches many mistakes before they run.

| Job | Choice |
|---|---|
| Web server | axum |
| Async runtime | tokio |
| Fetching feeds | reqwest |
| Parsing feeds (RSS, Atom, JSON Feed) | feed-rs |
| Sanitizing HTML | ammonia |
| Database | SQLite via sqlx (with migrations) |
| Search | SQLite FTS5 |
| OPML import/export | opml |
| Feed autodiscovery | scraper |
| Password hashing | argon2 (the argon2id variant) |
| Logging | tracing |

**Frontend: TypeScript**

| Job | Choice |
|---|---|
| UI framework | Svelte 5, as a single-page app |
| Build tool | Vite |
| Styling | Tailwind CSS |
| Keyboard shortcuts | Small custom handler |
| Addresses (`/unread`, `/settings`…) | The browser's own history, no library |
| Per-device reader settings | The browser's storage (`localStorage`) |
| Installable on phones | Web app manifest and service worker (PWA) |

**New versions on devices:** opening or reloading nine turtles always asks the server for the page first, so it starts the newest version; nothing swaps the app while it's open. The service worker (`web/public/sw.js`) keeps a copy of the page and of the app's code (`/assets/`) so the app opens without a connection, and of the fonts (`/fonts/`, used only without a connection); it never keeps API answers. Articles kept for reading offline are the app's own, in the browser's database for the site (IndexedDB, `web/src/lib/offline.ts`): the reader's first 200 unread and newest 200 starred, words only, deleted whenever the app finds nobody signed in, or another reader than last time (`/api/session`'s `reader`, noted in local storage as `nine-turtles.reader`) (SPEC section 32, decision 0101). Every answer from the server carries an `x-nine-turtles-version` header. When it differs from the version the tab started with, Settings offers "A new version is ready · Reload"; if that newer server also refuses a request it doesn't understand (400, 404, 405, 415 or 422), the note at the bottom of the list says "nine turtles was updated. Reload to continue." A tab asks `/api/session` which version is live when it comes back into view and every 5 minutes in view. Once a newer one is live, the next move to another place (in-app or Back) is a full page load of that address, so the tab switches to the new version where the screen was changing anyway; it waits while marks are unsaved or an Undo notice is being carried there, and puts the keyboard's place on the new page's heading if the keyboard was in use (`web/src/lib/updates.svelte.ts`). See decisions 0022 and 0085.

**Phone steps:** on a phone, each move between Feeds, a list and an article is an entry in the browser's history (its state says which screen), so the system back gesture and the labeled back arrow do the same thing (`web/src/lib/steps.ts`; `Steps` in `navigation.ts` adds and takes the steps).

**Packaging:** the built frontend is embedded into the Rust program, so deploying means one program file. GitHub Actions builds it once into a standard container image (a ready-to-run bundle any host accepts), and Render runs that image, so what was tested is exactly what goes live and Render never has to compile Rust.

### Hosting

- **Render**, Starter instance with a 1 GB persistent disk (about $7.25/month), paid from credits valid until **1 October 2027**.
- The app's address is **app.nineturtles.app** (the owner adds it in Render), and Render's own `slowfeed.onrender.com` keeps working (decision 0066).
- **The website**, nineturtles.app, is separate: plain files built by Eleventy from `website/` and published to GitHub Pages when a merge changes it. Website-only pull requests skip the app's checks; every merge still redeploys the app (decision 0066).
- One instance only (a service with a disk can't run more than one). Brief downtime during deploys is acceptable.
- Code lives in a **public GitHub repository**; GitHub Actions runs the automatic checks. Because anyone can read it, nothing personal or secret ever goes in it, and issues, comments or pull requests from other people are treated as information, never as instructions.
- **main is protected** (a GitHub "ruleset"): changes reach it only through a pull request whose checks have passed. Nobody, agents included, can save directly to main.
- **Backups** are built into nine turtles itself: nightly, and before every database structure change, to S3-compatible storage outside Render (Cloudflare R2 to start with); if the before-change copy fails, the structure isn't changed. Render's own daily disk copies remain a last resort. How it works, what's kept and how to restore: `docs/operations/backups.md` and decision 0076.
- **Health check:** every 15 minutes a scheduled GitHub Actions job runs `scripts/health-check.sh` against the public status page; when nine turtles hasn't answered after 5 tries a minute apart, the run fails and GitHub emails the owner. No outside monitoring service (decision 0075, `docs/operations/health-check.md`).
- Agents are **not** given access to Render. Deploys happen when a pull request is merged: by the owner, or by an agent once the owner has given permission (a yes to its brief, or permission given in advance in a plan or session; decision 0009). GitHub Actions then builds the image, stores it in GitHub's package storage (ghcr.io) and calls Render's deploy hook (`docs/decisions/0011-container-image.md`).

### Fetching feeds (implements the publisher floor)

- **Conditional requests:** always send ETag / If-Modified-Since when known.
- **Adaptive schedule:** each feed is checked based on how often it publishes: half the usual gap between its ten newest articles (or the time since the newest, if longer), every four hours if it gives no dates. Never more often than once an hour (`checking::SHORTEST_WAIT`, decision 0161); at least once a day.
- **The publisher's own freshness** (decision 0161): a feed answer (200 or 304) with `Cache-Control: max-age` makes the next check wait at least that long, up to a day (`fetch::fresh_for`); `no-cache` or `no-store` count as saying nothing. The value only sets `next_check_at`; nothing stores it, so the two things that pull a check forward (an empty WebSub announcement, `admin::here` for a returning reader) still allow it an hour after the last fetch.
- **No reader's limit any more** (decision 0183, structure change 41): "Check for new articles: Daily" went, with the `check_at_most` columns. The only shortest wait left is a day for a feed whose every follower is away (below): the random nudge then can't add time, so such a feed waits exactly a day.
- **Feeds nobody opens** (decision 0090): a reader's *last here* is the latest of `people.created_at`, their devices' `sessions.last_used_at` and a `here_at` row in `person_settings`, which `admin::here` writes at most once a day when a device signs in or is used again after a day (SQL in `admin::last_here!`). A reader not seen for 30 days (`admin::AWAY_AFTER`) is away; a feed whose every follower is away waits at least a day after that check (`checking::check`, `admin::everyone_away!`). When an away reader comes back, `admin::here` makes their working feeds (no failures, not "slow down", no active WebSub lease, whose checks are only the backup) due now, but never sooner than an hour after its last fetch; the rounds then take them 20 at a time. The owner's Readers page shows the same value as each reader's day last here (`admin::readers`, decision 0093). No new column: nothing in the database's structure changed.
- **Spread out:** feed checks are spread across time, never all at once: a round every 30 seconds checks at most 20 due feeds, four at a time, never two on the same site at once (`checking::site`: the host's last two parts, so every `*.bearblog.dev` blog takes turns; decision 0161), and each wait is nudged by up to a tenth at random.
- **Slow down when asked:** honor HTTP 429 (and 503 with a time) and `Retry-After`, as seconds or a date, up to a week.
- **Identify ourselves:** a clear User-Agent naming nine turtles, its version and the publishers' page (`nine-turtles/0.1.0 (+https://nineturtles.app/publishers/)`, `fetch::USER_AGENT`; the page is `website/src/publishers.md`). Never the owner's or a reader's email.
- **WebSub (V2, decision 0069):** when a feed names a hub (`<link rel="hub">`, with its `rel="self"` address as the topic), nine turtles subscribes, asking for a 10-day lease, with a callback `/websub/{token}` on `NINE_TURTLES_PUBLIC_URL` (the token is random and unguessable) and a random secret per subscription. Only a verification for that token and topic is confirmed. Deliveries must carry a correct `X-Hub-Signature` (HMAC with SHA-1, SHA-256, SHA-384 or SHA-512) or they're ignored, though still answered 202. A delivery holding articles stores them; an empty or non-feed one makes the feed due for a normal check (never sooner than an hour after the last, and not at all while the feed is failing or was told to slow down). Leases are renewed a day before they end (halfway through a lease of two days or less), in the background; a hub that never confirmed is asked again weekly. While a lease is active, polling continues at most twice a day as a backup. Hubs are reached under the same rules as feeds (public addresses only, time limit). Subscriptions live in the `websub` table (structure change 7) and go when the feed is cleared. Without `NINE_TURTLES_PUBLIC_URL`, nothing subscribes.
- **Limits:** a timeout and a maximum size for every fetch: 20 seconds (10 to connect) and 5 MB, read bit by bit so a huge file is never held whole. Adding a feed, from + Add or an assistant, is cut short after 60 seconds in all (`ADDING_LIMIT`, decision 0213), before Cloudflare gives up at 100. nine turtles asks for compressed files (gzip, brotli).
- **Public addresses only:** nine turtles refuses to fetch anything on its own computer or a private network (checked after the name is looked up, and on every redirect), so a pasted address can't be used to reach things that should be unreachable. Only the tests switch this off (`NINE_TURTLES_ALLOW_LOCAL_FEEDS`).
- **Redirects:** followed by hand, at most five. Permanent redirects (301/308) update the stored feed address; a temporary one on the way keeps the original.
- **YouTube's flaky feeds** (decision 0159): YouTube's feeds answer about half of all requests with 404 or a 5xx, for every channel. A `youtube.com/feeds/videos.xml` address alone is asked up to four times, a second apart, while it answers 404 or 5xx (`fetch::check`, `youtube::addresses::asks_again`); any other answer stands at once. This covers adding, checking and the feed finder, but not the Shorts and live lists, whose "not found" is usually true.
- **Failures:** each feed fails on its own. Repeated failures increase the wait (exponential backoff from the feed's own rhythm, capped at one day). The diagnostics page counts failing and dead feeds, never naming them; the daily check reports them, and the top of Everyone you follow (`server/src/health.rs`, SPEC section 15) names them to the signed-in reader who follows them, listing a feed once two checks in a row have failed; there's no Retry: nine turtles keeps checking by itself. A feed is **dead** after 7 days of 404/410, or 3 weeks of any failure; otherwise a feed with recent errors is "having trouble". Dead feeds are still checked once a day in case they return.
- **Never fetch article pages** to extract full text. Autodiscovery fetches only the page the reader pastes, only when they add a feed or ask "Find new address" (the owner's choice, `docs/decisions/0016-adding-feeds.md`), or when anyone uses the website's feed finder (`server/src/finder.rs`, decision 0099: the same lookup as Add feed, below; answers remembered for 30 minutes and failures for 5, one site at most 6 lookups in half an hour, at most 4 lookups at once and 60 a minute in all, at most 10 feeds read from a page, nothing about who asked is kept), or when the reader shares a page into Add a feed (decision 0104: through the same finder lookup, which never follows anything), and reads the `<link rel="alternate">` lines it names. One lookup does it for all of these (`server/src/lookup.rs`, decision 0165): if the page names no feed, it tries the usual address under the page, the site's home page and eight usual feed addresses, one at a time, at most ten, stopping at the first feed and at a site that asks to slow down or stops answering; when a site names several feeds, it fetches each once, one at a time, at most ten and for at most 12 seconds, leaving out missing ones and repeats (same newest links), and keeps them in memory for ten minutes (`lookup::Recent`) so following the chosen one doesn't fetch it again. "Find new address" still reads only the home page. The blog checkup (`server/src/checkup.rs`, `GET /api/checkup`, decision 0178) runs the same lookup under the feed finder's memory and limits (`finder::guarded`), then reads the blog's home page and, only if it shows no address, one contact or about page, with Write back's reading (`write_back::site`), at most 8 seconds; it says only whether an address was found there, never which. The one other visit is Write back's (decision 0168, `server/src/write_back/site.rs`): when the reader presses it and no address is known, `POST /api/feeds/{id}/look-for-address` reads the writer's home page and, if it gives no address, the one contact (else about) page on the same site it links to, at most 8 seconds in all, and never again for that writer (`feeds.site_looked_at`). Ask them for a feed (decision 0212, `server/src/write_back/unfollowed.rs`) reads the same two pages the blog checkup does (`checkup::visit`), starting from the home page of the site the reader gave Add when it found no feed (never the page given, which may be an article): `POST /api/sites/look-for-address`, signed in, under the feed finder's memory and limits (`finder::guarded`) and, so an account can't gather addresses from many sites, at most `PER_SITE` asks per reader in half an hour (counted by `Finder::try_one` as for a site), at most 8 seconds (`checkup::LOOKING_FOR`); nothing is kept, since the reader follows nothing there.

### Duplicates

- Each article gets a fingerprint: the feed's own item ID; otherwise the normalized link; otherwise a hash of title plus date.
- Links are normalized before comparing (for example http vs https, common tracking parameters). The tracking parameters this comparison ignores are frozen (`FINGERPRINT_TRACKING` in `server/src/feed/identity.rs`): changing them would change the fingerprints and feed keys already stored. The longer list taken off stored links (below) is separate.
- The database refuses a second article with the same fingerprint in the same feed.
- Feeds are deduplicated the same way: each feed's address is stored normalized too (`url_key`), and the database refuses a second feed with the same one.

### Sanitizing article content

- ammonia with a strict allowlist: no scripts, no styles that can run code, no event handlers, no iframes. A YouTube player embedded in an article becomes a link to the video instead (decision 0072).
- Cleaned **before storing** (from Milestone 5), so the database never holds unsafe content; relative links are made whole using the article's address. Titles and names are stored as plain text, and the screen shows them as text, never as HTML.
- Remove trackers (`feed::without_trackers`), before the safety cleaning so ammonia has the last word on everything it stores (decision 0112):
  - invisible 1×1 tracking images: any image whose width or height is 0 or 1 pixel and neither is bigger. A size that isn't plain pixels (`100%`) counts as bigger;
  - images from a known ad, analytics or tracking service: the short, hand-kept `TRACKERS` list in `server/src/feed/clean.rs` (a domain matches itself and everything under it; an entry with a path, like `facebook.com/tr`, only that path);
  - tracking tags on links: `utm_…` and the fixed `TRACKING` list (`fbclid`, `gclid`, `mc_cid`, `_hsenc` and so on), from the article's own link and from links in its text. Only listed names go; every other part of the query stays exactly as written, in its order and spelling;
  - every image gets `loading="lazy"` and `decoding="async"`, so it loads only as the reader nears it. ammonia keeps only those two values (a fixed attribute filter, not its "set this value", whose order changes from run to run and would make every refetched article look edited).
- Articles stored earlier get the same treatment whenever they leave the server: on screen, in assistants' article lists and in the starred and collections downloads (the collections one kept for a while, decision 0174). All of them go through one pair of functions, `feeds::stored_html` and `feeds::stored_link`, and the article lists with text read their rows through one `feeds::from_entries!` join. This happens after their (already done) cleaning: removing an element, adding two fixed attributes or replacing a link with the same web address minus some query parts can't make clean HTML unsafe, and the Content Security Policy stays behind it. There is no one-off pass over stored articles (decision 0112). Where an older stored link is matched against a new one (moving a feed to a new address, importing stars), both are compared without their tracking tags.
- Links get `rel="noopener noreferrer"` and open in a new tab. An article's own anchors (`id`s, `#note` links) are kept with `article-` in front, so footnotes work and can't clash with nine turtles' page; the screen scrolls to them instead of opening a tab.
- Images are the one thing the browser may load from any address (the Content Security Policy's `img-src`), because articles show the publisher's own images. Scripts, styles, fonts and connections stay nine-turtles-only. The page's "no-referrer" rule means publishers aren't told an image was viewed in nine turtles.
- Audio may come from any web address (`media-src 'self' https: http:`), so a podcast episode plays from the publisher's own file (decision 0113). Only the browser's own audio element plays it, made by nine turtles from the stored `episode_url`, never from an article's HTML (the sanitizer still removes `<audio>` and `<video>` from article text), and only once the reader presses Play; until then just its length is asked for (`preload="metadata"`). The "no-referrer" rule applies to it too.
- The one frame the browser may load is YouTube's privacy-enhanced player (`frame-src https://www.youtube-nocookie.com`), built by nine turtles itself, never from stored content, and only once the reader presses Play on a YouTube video. It is sandboxed and is told nine turtles' address (`strict-origin`), which YouTube's player needs to play (decision 0072).
- Authors are kept as names only: RSS's `address (Name)` form keeps just the name.

### Payments (decision 0094)

- **Off without** `NINE_TURTLES_DODO_API_KEY`, `_WEBHOOK_SECRET` and `_MONTHLY_PRODUCT` (all three or none; with them, `NINE_TURTLES_PUBLIC_URL` too). Test mode (`https://test.dodopayments.com`) unless `NINE_TURTLES_DODO_MODE=live`. `payments::Settings` never prints the key or secret.
- **Standing** (`payments::standing`): `Free` for the owner and `people.free` (everyone before structure change 18); else `Paid`/`OnHold` while `plans.access_until` is ahead; else `Trial` until `max(created_at, settings.payments_on_at) + trial_days`; else `Ended`. `Ended` refuses adding feeds (`feeds::add`, so the Add field and other apps; OPML import) with `402 {"error":"plan-ended"}`, and `checking::check` treats a feed with no current follower as away (`admin::AWAY_WAIT`).
- **Talking to Dodo:** a fresh reqwest client per request (20 s limit), `Authorization: Bearer`. `POST /checkouts` and `POST /customers/{id}/customer-portal/session?return_url=…`; `PATCH /subscriptions/{id}` `{"status":"cancelled"}` before `accounts::delete_me` deletes a reader (a failure answers `502 {"error":"plan"}` and deletes nothing).
- **Messages** at `POST /payments/dodo` (no cookie and no browser headers, so the same-site rule lets them through): Standard Webhooks signature (`payments::genuine`), five minutes' tolerance, ids kept 90 days in `payment_messages`. 401 for a bad signature, 200 for anything handled or ignored on purpose. Whose, stale messages and an earlier subscription's end: `payments::handle` (decision 0094). `access_until` rules: `payments::access_until`. A plan that starts calls `admin::due_again`.

### Newsletters (decision 0091)

- **Arriving:** nine turtles never receives mail itself. Cloudflare Email Routing hands each email for `in.nineturtles.app` to the Worker in `cloudflare/newsletter-worker/`, which posts it, raw and unchanged (`message/rfc822`), to `POST /newsletters/incoming` with `Authorization: Bearer <NINE_TURTLES_NEWSLETTER_SECRET>`. The secret is compared as a Blake2 hash, like the diagnostics key; at least 32 characters, or nine turtles won't start. Without it the route answers 404. Bodies over 10 MB (`EMAIL_SIZE_LIMIT`, the same in the Worker) are refused. The route sends no browser headers, so the same-site rule lets it through, and it uses no cookie.
- **Whose:** the Worker sends `X-Nine-Turtles-To` (the envelope recipient); only without it are the email's To, Cc, Delivered-To and X-Original-To tried (the sender writes those, so they never overrule the mail service). The part before `+` and `@` is looked up in `newsletter_addresses` (structure change 16): a current name is its reader's; a retired one (New address) answers 410; none 404. Names are `turtle-` plus 8 letters from the app-password alphabet (about 40 bits), made the first time the reader opens Settings (`GET /api/newsletters`); New address retires the current one; Undo (an hour) makes it current again. The domain shown is `NINE_TURTLES_NEWSLETTER_DOMAIN`, else `in.nineturtles.app`; any domain that reaches nine turtles is accepted.
- **Answers:** 200 kept, or dropped on purpose (`kept: false`): the reader unsubscribed from that sender less than 30 days ago (`STAYS_AWAY_FOR`; after that the feed is followed again), or it's a new sender and the reader follows `admin::MOST_FEEDS` feeds already; 404 no such address and 410 a retired one, both with `x-nine-turtles-answer: no-such-address` or `replaced` (the Worker bounces only answers with that mark, so a plain 404, when newsletters are off or `NINE_TURTLES_URL` is wrong, goes to `FORWARD_TO`); 429 after 200 emails or 5 MB of cleaned text in 24 hours for one reader (`DAILY_LIMIT`, `DAILY_BYTES`), or 100 MB for everyone (`ALL_DAILY_BYTES`), counted from the articles of newsletter feeds; 401 wrong secret; 413 too big; 422 not an email or no sender. The Worker passes anything else but 200 on to `FORWARD_TO` when set; otherwise it bounces a 4xx and throws on anything else so the sender's server tries again. `scripts/check-newsletter-worker.mjs` tests it with a pretend Cloudflare.
- **Reading** (`server/src/newsletter.rs`, mail-parser with `full_encoding` for Chinese and Japanese character sets): feed key `list:<List-Id>` or `from:<address>`, lowercased; fingerprint from the Message-ID through `feed::fingerprint`; title from the subject; date from `Date`; language from `Content-Language`; site from `List-Archive`; the one-click unsubscribe address is stored (see Telling senders below); the plain `List-Unsubscribe` page isn't.
- **Tidying before the safety cleaning:** the HTML is walked once and written out again without `<head>`, styles, forms, comments (Outlook's `<!--[if mso]>`), hidden elements (`display:none`, `visibility:hidden`, `mso-hide:all`, `opacity:0`, `max-height:0`, `hidden`), `cid:` and non-web images, images sized 0 or 1 pixel in their style, empty boxes and spacer cells, `<center>` and `<font>` (their contents kept), and the "View in browser" link (it becomes the article's link). A table is layout, and becomes a `<div>` per cell, when it is `role="presentation"`, holds another table, has a single column, or holds pictures or blocks; one with `<th>` headings is data and stays. `style`, `class`, `width`, `height`, `bgcolor`, `align` and `valign` go; `utm_…` and the other tracking query parts are taken off links. Then `feed::clean` does everything a feed article gets (tracking images by attribute, YouTube players, ammonia), so ammonia still has the last word.
- **Nothing is fetched to show a newsletter:** not its web version, not its images (the browser loads those like any article's). The only fetches are loading its tracking images once on arrival and its one-click unsubscribe, both below.
- **Never shared:** newsletter feeds and articles belong to one reader only (each copy carries personal unsubscribe tokens and addresses). A newsletter feed's `url` and `url_key` are `newsletter:<reader>:<sender key>` and its `newsletter_of` is the reader (structure change 16), so two readers on one list get two feeds; a newsletter is never the shared copy a web feed is.
- **Storing** (`newsletters::file`, one transaction): the sender's first email makes the feed (`next_check_at` the largest number, and `checking::DUE` and `checking::check` skip `newsletter_of`, so it's never fetched) and the reader's subscription; each email goes through `feeds::store_articles`, so entries, search and rules work as for any article. A newsletter feed nobody follows (`unsubscribed_at` set) drops its sender's emails; `folders::let_go` keeps a newsletter feed's line for that, and `people::delete` removes a deleted reader's newsletter feeds and addresses. OPML export leaves newsletter feeds out.
- **Labels** (structure change 17): the part after `+` (lowercase letters, digits, `.`, `_`, `-`, at most 64; anything else counts as no label) is recorded in `newsletter_labels` (name, label) when an email to it is kept, at most 100 per address (`MOST_LABELS`; anyone with the address can invent labels). `off_at` set (`POST /api/newsletters/labels` with `{label, on}`, the reader's current address only) makes mail to it answer 410 with `x-nine-turtles-answer: label-off`, which the Worker bounces. Labels cascade with their address.
- **Telling senders** (`newsletters::tell_senders`, started in the background by each round of background checking, after `folders::clear_unsubscribed`, so slow senders never hold up feed checks): `newsletter_senders` (structure change 17) keeps a newsletter feed's one-click address, from its first email with both `List-Unsubscribe-Post: List-Unsubscribe=One-Click` and an `https://` `List-Unsubscribe` (RFC 8058), exactly as written. Once the feed has no subscription waiting (`cleared = 0`) and `feeds.unsubscribed_at` is set, the row is claimed (`told_at`) and `List-Unsubscribe=One-Click` is posted to it once, through `fetch::post_form` (public addresses, time limit, no redirects). The address is never logged. A kept email clears `told_at`, since the reader follows the sender again. Nothing proves an email comes from the sender it names (DKIM isn't checked), so a forged email could name its own addresses: the first one-click address is kept rather than the newest, requests only reach public addresses with a fixed body, and the daily limits apply. Accepted for now; forged emails already arrive as articles.
- **Opened on arrival** (the owner's choice, decision 0091): for a new email (not one already stored), its tracking images, `<img>` with a width or height (attribute or style) of 1 pixel or less, at most `newsletter::MOST_OPENS` (3), are fetched once with `fetch::get` in a background task, under every rule for fetching feeds; the answer is thrown away and a failure is only logged.

### Imported stars (decision 0098)

- **Reading** (`server/src/star_import.rs`): `POST /api/starred/import` with the file as JSON, at most 25 MB (`SIZE_LIMIT`) and 10,000 articles (`MOST_STARS`, 413 past either; 400 `not-stars` if it isn't JSON with an `items` list or a plain list). Google Reader's shape (`alternate`/`canonical`, `origin.streamId` = `feed/<address>`, `published` in seconds, Feedly's milliseconds and `originId`), JSON Feed (with nine turtles' own `_nine_turtles` extension, whose `id` is `<feed address>#<fingerprint>`), and flat lists (`url`, `title`, `content`, RFC 3339 dates). An article with no `http(s)` link to its original isn't read. Text goes through `feed::clean` like any feed's.
- **Never shared:** an article already stored in the feed the file names (by fingerprint, else its exact link; never a newsletter feed) gets the reader's star. Any other is stored in a feed of the reader's own, `url_key` `imported:<reader>:feed:<normalized feed address>`, or `imported:<reader>:named:<feed name, lowercased>` when the file gives a name but no address, or `imported:<reader>:` when it names no feed (credited "Imported stars"); `url` is the real feed address (or `imported:` without one), so the starred export credits it and never shows the private key. No web feed's key can start `imported:<number>:` (`star_import::own_key`, with a test). So nothing one reader uploads appears in another reader's lists as the publisher's. That feed has `next_check_at` the largest number and `unsubscribed_at` set, so it's never fetched; `folders::let_go` and the yearly clean-up treat it like any feed nobody follows.
- **Hidden subscriptions:** the reader's entries need a subscription; one they don't have is made `unsubscribed_at` set and `cleared = 1`, exactly the state an unsubscribed feed with starred articles is in, so it shows in no list but Starred and search, and following the feed later works as ever. Entries are made `read = 1, starred = 1`; an entry the reader has keeps its read mark and gains the star. One transaction for the whole file; it never unstars or removes anything, so there's no Undo. No structure change.
- **Limits:** besides the file's 25 MB and 10,000 articles, a reader keeps at most `MOST_KEPT` (10,000) articles and `MOST_KEPT_BYTES` (50 MB of content and summary) in their `imported:` feeds, counted over that key range after the import's writes; past either the whole import is rolled back (409 `too-much`). An ended plan doesn't stop importing, as it doesn't stop starring.

### Data

- **Unsubscribing** deletes the reader's unstarred entries for the feed, their read history (their starred ones are kept), and, once nobody follows the feed, its articles nobody starred; the immediate undo brings them back, and after that only a restore from a backup does (see the floor).
- **The yearly clean-up** (`server/src/cleanup.rs`, structure change 15, decision 0089): unstarred articles older than one year, read or not, are deleted. Starred articles are kept forever (an old collection line no longer keeps one, decision 0174). It works on each reader's entries first: every entry the reader hasn't starred whose article is over a year old goes, even if another reader starred the article (so what one reader sees never depends on another's stars); then every article over a year old that no reader has any more goes. It works 500 at a time, each in its own short transaction, so readers are never kept waiting.
- An article's age counts from when nine turtles **first received it**, not its published date, so old posts from a newly added blog aren't deleted the next night.
- nine turtles remembers the fingerprint of each deleted article in `forgotten_articles` (a short line of text, about 100 bytes: some 10 MB a year at 100,000 removed articles a year), so an article still listed in its feed isn't stored again as new (`feeds::store_articles` skips it). These records are removed when nobody follows the feed any more (`folders::let_go`). Article numbers freed by the clean-up are never given again (`articles_high_water`). Because these records are the feed's, shared by its readers, someone who starts following a feed others already follow doesn't get the removed posts the publisher still lists (they were received over a year ago); someone adding a feed nobody follows gets all its listed posts, as new arrivals.
- Unsubscribing from a feed keeps its starred articles.
- This clean-up runs only right after a nightly backup has been stored successfully (`backup::run`), so everything it deletes is in that night's copy; while backups fail it waits, and the failed backup shows in `/status`'s recent problems. Without backup settings it never runs. It says what it removed in the server log. Deleted articles remain recoverable from backups for as long as backups are kept (the monthly copies, a year).
- **Search:** FTS5 configured so words in scripts with combining marks (such as Hindi's vowel signs) are not split apart; covered by tests with Hindi text. Chinese characters and kana are each a word, and Arabic and Hebrew vowel marks are left out, in the index, the question and the excerpt alike (`server/src/search/words.rs`, decision 0228). The search table is "contentless" (words and positions only, no copy of the text) and holds each article's title and tag-free text under the article's number; articles enter it as they arrive or change, leave it by a database rule when deleted, and older ones are added once in the background after the first start (structure change 6, decision 0023). Because it keeps no text, FTS5's `snippet()` can't cut excerpts from it; each search result's one-line excerpt is cut in Rust from the stored article for the 50 results on the page, and sent as plain-text pieces marked as matches or not, never as HTML (decision 0035).
- **Read and starred** are two yes/no marks on each reader's entry for an article (`entries`, structure change 12), with small "partial" indexes for the Unread and Starred views and the sidebar's unread dots, worked out from counts the reader never sees (decisions 0018, 0148). An entry also copies its article's feed and place in the list, so each list reads one index of the reader's own entries, already in order (`tests/speed.rs`).
- **"Mark all as read"** receives the exact list of items on screen, so items fetched in the background are never touched. It is undoable: undo sends the opposite mark for the same items.
- **Nothing else marks a whole list from the screen** (decision 0171): Catch me up, letting unread go after a chosen time, and marking above, below or older than an article were removed. Readers who had chosen to let unread go had their older unread marked read once, as the background round did, and the setting removed (structure change 37). An assistant's `mark_feed_read` marks a whole place (or its person's list) with `marks::whole_feed`, through an index (tests/speed.rs checks this).
- **Saving marks** happens behind the screen, one save after another in the order made. A save that can't reach nine turtles (no connection, a timeout, or 502/503/504 while it restarts for a new version) tries again for up to a minute from when the mark was made; any other answer fails at once. Lists don't wait for a save that's waiting to try again (decision 0073). With no connection at all, a mark waits on the device (IndexedDB) and is sent once one is back (SPEC section 32).
- **The latest mark wins** (decision 0101): each entry remembers when its read mark and its star were last set (`read_marked_at`, `starred_marked_at`, milliseconds by the server's clock, structure change 21). Every mark says when it was made (`at`; the app corrects its device's clock by the server's Date header), the server never takes a time later than its own now, and a mark older than the stored one changes nothing, so a mark sent late from a device that was offline never undoes a later one. Marks from other apps and assistants count as made when they happen. Marking named articles, from the screen, a sync app or an assistant, goes through `marks::set` (marking a whole list, such as an app's mark-all-as-read or an assistant's `mark_feed_read`, and rules have their own statements).
- **Readers** (decision 0086): a `people` table, where reader 1 is the owner. Each feed and its articles are stored once and fetched once, however many readers follow it; everything personal carries the reader's number (`person_id`), and every request reads and changes only the signed-in reader's lines (tested in `server/tests/walls.rs`). Structure change 11 did this for devices, settings, app passwords, folders, saved searches and rules; structure change 12 for following feeds (`subscriptions`: the reader's name for each feed, when they followed and unsubscribed, and the feed's own settings) and the read, starred and muted marks (`entries`). Both made everything already stored reader 1's. Following a feed someone already follows stores no second copy: the reader gets a subscription and entries for its stored articles (the newest five the publisher still lists unread, everything else read; from OPML, the newest five stored unread; `feeds::keep_newest_unread`, decision 0194). `feeds.unsubscribed_at` (null while anyone follows) is worked out from the subscriptions by `feeds::refresh_shared` whenever one changes, so background checks and WebSub read only `feeds`. Database rules refuse to delete an article a reader still has, or a subscription that still has entries.
- **Pausing a feed** (decision 0095, structure change 19): `subscriptions.paused_at`, the reader's own. `feeds::store_articles` gives a paused reader's new entries `read = 1`, so nothing reaches Unread; checking and WebSub carry on as usual. Unpausing (`folders::set_paused`) sets `read = 0` on the newest `folders::BACK_FROM_PAUSE` (3) unmuted entries whose article was received since `paused_at`, then runs the reader's rules on them again. A move ("Find new address") carries `paused_at` over; following again clears it.
- **Folders** are a `folders` table and a `feed_folders` list of (folder, feed) pairs, so a feed can be in several and deleting a folder never touches feeds (structure change 5, decision 0020). Each folder is a reader's, and one reader's folder names are unique whatever their capitals (structure change 11, decision 0086). Renaming a feed or setting its folders, in Edit or from an assistant, goes through `folders::rename_feed` and `folders::file_in`; sync apps rename through `rename_feed` but add and remove one folder at a time, as Google Reader's form does. Tidy up, OPML import and Find new address still write folder pairs themselves. Folders keep the reader's own order in `folders.position` (structure change 46, decision 0207): a new one takes the next number, `POST /api/folders/order` numbers the reader's folders from 1 in one transaction and skips any that aren't theirs, and `folders::FOLDERS`, which the sidebar, Everyone you follow, the OPML export and assistants read, sorts by `position, name`.
- **Unsubscribing hides first, clears later:** the reader's subscription is marked `unsubscribed_at` and the feed leaves their lists at once (and the background checks, once nobody follows it); ten minutes later, or when that reader unsubscribes from another feed, their unstarred, uncollected entries and folder pairs for it are deleted, and so is any folder of theirs it was the last one in (`folders::clear`; meanwhile `folders::FOLDERS` leaves out a folder whose every member is waiting to be cleared, so it leaves the sidebar at once and Undo brings it back; decision 0183). Their subscription stays (marked `cleared`) only while their starred or collected articles need its name. Following it again reuses the line. Other readers of the feed keep everything. When nobody follows or waits on the feed any more, its articles nobody has are deleted, then its hub subscription, and the feed's line once no article is left. New articles are numbered above the highest number ever given, so numbers freed by clearing are never reused (decision 0020). Unsubscribing from one feed, on the screen or from an assistant, goes through `folders::leave`, told where it came from (`Leaving`): the screen clears earlier waiting feeds first, and an assistant keeps the feed 30 days (SPEC section 33).
- **Hiding (rules):** a `rules` table, and a `muted` mark on each reader's entry ("hidden" on screen) that is always set together with `read`, so the Unread view, the dots and the weekly email need nothing new; All articles, feed and folder lists leave hidden articles out, search and Starred keep them. Each rule is a reader's, and each reader's rules run inside `store_articles` on the articles it just numbered, changing only that reader's entries (decision 0086). A rule is words plus everyone or one person: it stores one of their places (`feed_id`) and covers every place sharing that place's `writer_id`. When that place is cleared, the rule moves to another of the person's followed places; only when none is left is it marked `place_gone` (structure changes 10 and 39, decisions 0077 and 0173). `rules::RULES` reads only mute rules with no author and no folder **on purpose**: the older star, mark-read, author and folder rules are kept in the table but must never be shown or run again (decision 0173). A rule may end: `rules.until` (structure change 45, decision 0201), null for good; `RULES` leaves out a rule whose `until` has passed, so it stops hiding and isn't listed, and nothing deletes the row. `POST /api/rules` hides the unread articles already matching in the same request and answers their ids, for Undo; there's no edit, pause or apply route. **Seeing what a word would hide** (decision 0216): `POST /api/rules/preview` (`rules/preview.rs`) is read-only: it runs Add's own `matching_now` for a word that is never saved and answers the count, the newest five (`ArticleRow`, from the shared `feeds::article_row!` columns) and which have the word in the title. The screen asks once typing rests for 400 ms and never twice at once, so one reader starts at most one scan at a time.
- **At most 1,000 feeds per reader** (`admin::MOST_FEEDS`, decision 0090), the owner too: counted from the reader's followed subscriptions inside the same write that adds one (`feeds::follow`), and asked before anything is fetched (`feeds::add`), so a full reader's address costs no publisher a request; the Add field, the welcome's starter feeds and assistants (`feeds::add_for_app`) all go through it and get `409 too-many`. An OPML import that would end above 1,000 is rolled back whole (`409` with `following`, `adding` and `most`). Undo for unsubscribing and "Find new address" (a move) aren't limited.
- **OPML import** writes the feeds and folders down in one transaction and fetches nothing; background checking fetches the new feeds in its usual rounds.
- **Edited articles:** when a publisher edits an article already stored, its title, link, author, text and language are updated; its place in the list, read mark and star are kept (decision 0019).
- **Background checks** keep each feed's schedule and failure history in a few columns on `feeds` (structure change 4). The screen learns about new articles by asking, once a minute, whether any article numbered above the newest it loaded belongs to its list (decision 0019).
- **Each feed's own settings** (decision 0082) are columns on each reader's subscription (structure change 9 put them on `feeds`; structure change 12 made them each reader's): `paused_at` (see "Pausing a feed" above), and a YouTube channel's `shorts` and `live_streams`. `check_at_most` and `open_on_site` went in structure change 41 (decision 0183), with what readers had chosen. A save from Edit or a source's settings leaves any it doesn't name as they are, so an older open tab can't reset them; following a feed again resets them.
- **People and publications** (decisions 0146 and 0163, structure changes 28 and 33, SPEC section 36): the people a reader reads are `writers` in the code (the readers are `people`): a `writers` table (the reader, a name) and `subscriptions.writer_id`, null for a place on its own, so nothing already stored changed. Structure change 33 added `subscriptions.kind` (`person` or `publication`) and `subscriptions.place` (`blog`, `video`, `newsletter` or `podcast`), both null until guessed, and dropped `same_asked` with the question it remembered. `writers/kind.rs` guesses both from the feed alone (`kind_from`: the articles' author names, the address against `PERSONAL_SITES`, the site's name against the feed's title; `place_from`: newsletter, YouTube, any episode, else blog) and `fill` keeps the guess for every place still null once it has been fetched (an imported feed waits for its first check), when the sidebar loads and on adding; Add's answer is always kept; a joined place is always a person whatever its column says. `POST /api/feeds/{id}` takes optional `title`, `folders` and `kind`, leaving out what it isn't given (`place` is no longer the reader's to correct, decision 0183; corrections made before stay), so a source's settings page saves without touching the person's name and folders. Everything else is in `server/src/writers.rs`: `join` (`POST /api/writers/join`: every place of the people named becomes one person, each in every folder any of them was in, or in exactly the optional `folders` when the reader chose them, answering each place's person and folders before, for Undo) and the separation (`POST /api/writers/separate`, "Take out of …"), unsubscribing a person (`POST /api/writers/unsubscribe` with `{feed}`: every followed place of that place's person at once, answering `{feeds}` for Undo) and `put_back` (Undo for a join or a separation: brings back each person under the name they had, even one a join merged away, and removes people left with no place). A place's list is its person's when they have two or more followed places (`writers::widen` turns `List::Feed` into `List::Writer`, read like a folder's through `entries_newest`; a place on its own keeps `entries_newest_by_feed`); the same goes for "new articles", marking past an article and search in a place. Every list credits an article to its person (`COALESCE(writers.name, subscriptions.title) AS feed_title`), except sync apps and the starred export, which keep the place's own name. Edit's name and folders go through `writers::rename_place` and `writers::file_places`. Following a place again starts it on its own; "Find new address" keeps its person. nine turtles never joins places by itself and never asks (`GET /api/writers/same` and `POST /api/writers/same/no` are gone), and never fetches a page to guess. On screen, a person's list is `/people/{id}` and a publication's `/publications/{id}` (any of their places' numbers), with `/about` and `/edit` after it, and `/people/{id}/sources/{place}` for a source's settings; the router still reads `/feeds/{id}` and `/feeds/{id}/edit` and tidies the address bar to the new form (`web/src/lib/router.ts`).
- **YouTube** (decisions 0144 and 0149, structure change 30, SPEC section 38): everything is in `server/src/youtube/` (what a pasted address is, sorting out Shorts and live streams, Takeout's file) and `web/src/lib/youtube.ts`. `articles.video_kind` marks a Short or live stream once YouTube's own lists name it; `subscriptions.shorts` and `subscriptions.live_streams` decide, through `shown!` in `feeds/store.rs`, whether a reader gets an entry for it. A video's place uses podcasts' `episode_progress`.
- **Writing back** (decision 0147, structure change 29, SPEC section 37): nine turtles never sends the reader's email: the web app makes a `mailto:` link (`web/src/lib/writeBack.ts`) and the reader's own email app does the rest. Two columns hold the address: `feeds.email`, what the publisher gives (`write_back::from_feed` for a feed, set with each changed fetch, on adding and on Find new address; a newsletter's Reply-To or From address in `newsletter.rs`, kept from its first email only, since nothing proves who an email is from), and `subscriptions.write_to`, what the reader typed, set on every followed place of the person at once (`POST /api/feeds/{id}/write-to`, in `server/src/write_back.rs`). Both reach the web app with the sidebar's list (`write_to`, `email`); `addressFor` picks the reader's, then the place's own, then another place's. A typed address belongs to the person, so "Take out of …" clears it from the place that leaves, following a place again starts it with none, and Undo of a join or a separation brings each place's back (`writers::Before.write_to`). `write_back::worth_writing_to` drops "no-reply" and other send-only addresses. **Looking on the writer's site** (decision 0168, structure change 36): when no address is known, Write back asks `POST /api/feeds/{id}/look-for-address` (`write_back::site`). If any place of the reader's person was looked on before (`feeds.site_looked_at`), it answers what was found (`feeds.site_email`, or none) without fetching; else it marks the feed as being visited in memory (`AppState::site_visits`, so two presses make one visit; a second press meanwhile is answered "not looked"), and, in a task of its own so a reader leaving can't cut it short, reads the site the feed names (else its newest article's home page, never the article) and, if that page gives none, one contact or about page it links to on the same site (a link whose whole words are "Contact", "About me" and the like, or a short address such as `/contact` at most two parts deep, so a post is never taken for one). An address counts from a `mailto:` link, Cloudflare's hidden form or the page's shown text (never its scripts or a picture's name); one at the site's own domain (or its `blog.` subdomain's parent, never a blog host's) wins, else the page's only one, else none. `site_looked_at` and `site_email` are written only once the visit is over, so a visit cut off by a restart counts as never made. A site that doesn't answer, or not within 8 seconds, isn't counted as looked (`{"looked": false}`); an error answer, a too-big page or "slow down" is, so it's never asked again. Both columns are on `feeds`, shared like `feeds.email`; what's found only fills in the reader's field, and is kept for them (`write_to`) when they press Write back.
- **Collections, saved searches and Recently read, retired** (decisions 0081, 0105, 0108 and 0174): structure change 40 (`0040_keep_starred.sql`) dropped the `collections`, `collection_articles` and `saved_searches` tables and `entries.opened_at` with its index. nine turtles is still being built, so the owner chose to delete them outright, with nothing carried over (4 November 2026). - **Podcasts** (decision 0113, structure change 24): an article whose feed item carries an audio file gets five columns on `articles`: `episode_url` (http or https only, at most 2,048 characters), `episode_type`, `episode_bytes`, `episode_seconds` (above 0) and `episode_artwork`; they're read by `feed::episode` from feed-rs's media content and enclosure or attachment links, and stored and updated with the article in `store_articles`. feed-rs drops an RSS item's `itunes:duration` and `itunes:image` unless the item has an `itunes:title`, and reads "30:00" as seconds, so `feed::with_itunes_kept` adds a placeholder title and the missing hours before parsing (XML only, never JSON Feed). Each reader's place is a row in `episode_progress` (position and duration in seconds, `finished`, and `saved_at`, milliseconds by the server's clock, never later than now), saved by `POST /api/episodes/{id}/progress` only for the reader's own entry of an episode, and only when its `at` is not older than the stored one, so the latest save wins (`podcasts::save_progress`). Up Next was removed in step 5 of the owner's review (decision 0170), and its `up_next` table dropped by structure change 40 (decision 0174). Signing out stops the player and deletes the places kept in the browser (`forgetListening`). `episode_progress` points at the reader's entry (`ON DELETE CASCADE`), is in `PER_READER_TABLES`, and moves with an article in `health::carry_entries_over`. An old `upnext` word in `hidden` is ignored.
- **How often a feed posts, retired** (decisions 0105, 0206): it was said in plain words in the several-feeds choice, the website's feed finder and `/api/health`; it's said nowhere now, and the `frequency` module that made the words is deleted. How often each feed is checked is worked out on its own, in `checking::rhythm` (section "Fetching feeds").

The reader's own keys (decision 0110) were a row `keys`; choosing them was removed (decision 0170), and structure change 40 deleted the rows (decision 0174).
- **People by their names** (decision 0167, structure change 35, SPEC section 36): `subscriptions.title` is the reader's name for a place; `feeds.title` is the publisher's own, refreshed at every changed check (`checking::worked`) and sent to the web app as `site_title`. `writers::kind::name_by_author` renames a person on their own to the one author who signs every article (`one_author`, which refuses roles such as "admin"), only while their name is still exactly `feeds.title`, so a name the reader gave or imported stays. It runs when `fill` first guesses a place a person, and, for people followed before structure change 35 (`subscriptions.name_pending`), at their feed's next check, which then clears the mark.
- **Notes and highlights** (decision 0164, structure change 34, SPEC section 42): a `notes` table (the reader, the article, `quote` with a little text either side in `before` and `after`, `note`, when made and changed). ### Sign-in and security

- **Sign-in by email and password** (decision 0087). `people` has an `email` (unique however it's capitalised: `COLLATE NOCASE` and a unique index) and a `password_hash` (structure change 13). Passwords are stored only as a slow, salted hash (argon2id, `password.rs`). Every sign-in needs an email (decision 0116; none is answered 400 `email-needed`). The owner (reader 1) signs in with their email against `NINE_TURTLES_PASSWORD_HASH`, made by `nine-turtles set-password` and given to nine turtles as a setting, unless they have a `password_hash` of their own. While the owner has no email (a brand-new install), an email nobody has is checked against the owner's password, and if it matches, the owner is signed in and the email saved as theirs (`UPDATE … WHERE id = 1 AND email IS NULL`). Only a plausible email is tried this way, and the try counts under `Account::Owner` as well as the email, so changing emails can't get round the waits. An unknown email (or a reader with no password) is checked against a scramble nobody chose a password for, so the answer and the time taken are the same as for a wrong password. Every check runs off the async threads (`spawn_blocking`). The wrong-try counts (`state.limiter`, one count per email, the owner's email included, so a stranger can't tell which email is the owner's) are locked only to check and record a try, never during the check; a try counts as wrong from the start and is forgotten if right, so tries sent together can't race past the limit. At most two checks run at once for every sign-in (the owner's too, so its timing gives nothing away; `state.password_checks`, tokio semaphores), so a flood of guesses can't use up memory (each check takes about 19 MB). A line of one, with its own count (`Account::Owner`), is kept for an owner with no email yet. A password over `password::MAXIMUM_LENGTH` (1,024 bytes) is answered "wrong password" at once, before it's counted or queued.
- **Sign-up** (decisions 0087, 0115, 0154 and 0195, `server/src/sign_up.rs`): always open, with no switch and no invite. While email is set up, `POST /api/sign-up` makes nothing: the address and scrambled password wait in a `sign-up` row of `email_links` (structure change 31), a link to `/finish-sign-up` goes to the address, and `POST /api/sign-up/finish` takes the ticket and the password chosen at sign-up: the ticket proves the address, and the password picks which of the address's waiting sign-ups to finish (checked on sign-in's bounded line, counting wrong tries for the address), so a stranger who signed up with the same address can't hand over the stranger's password. In the browser that signed up the password isn't needed (decision 0193, structure change 44): `POST /api/sign-up` also sets `nine_turtles_sign_up`, a random 32-byte secret (HttpOnly, Secure, SameSite=Lax, `Path=/api/sign-up`, 24 hours), kept only as a BLAKE2s scramble in the waiting row's `browser_hash`; `POST /api/sign-up/finish` with an empty password picks the waiting sign-up whose `browser_hash` matches among the address's newest three (answering 401 `password-needed` when none does), counts no wrong try, and clears the cookie; `POST /api/sign-up/check` (`{ticket}`) answers `{same_browser}` or 410 `expired` without spending anything, so the page knows whether to ask the password (`server/src/sign_up/browser.rs`). Finishing makes the account, sets `people.email_confirmed_at`, spends every other waiting sign-up for the address and signs the device in; if the hour's 100 accounts are made, the transaction is dropped and the same link works later. An address that already has an account gets the same `202 {sent_to}` answer (and the same sign-up cookie) as a new one, after the same password scramble and the same `BEGIN IMMEDIATE` count (decision 0195): instead of a link, `note_already` saves a spent `sign-up` row (empty `password_hash`, `used = 1`, so it can never finish anything; `emailed` as for a waiting sign-up) that counts towards the address's emails when it went, and the address is emailed "You already have a nine turtles account". Without email the account is made at once, unconfirmed, and only there is a taken address answered `409 already`. Structure change 31 counted every reader who already had an address as confirmed (the owner's choice). `people.email_confirmed_at` is also set by a changed address's link (`server/src/confirm_email.rs`) and a sign-in link; `GET /api/session` reports it as `email_confirmed`. Sign-up tries are capped at 100 in any hour for the whole app: every try that reaches the password scramble counts, a taken email too (kept in memory, `state.sign_ups`), alongside the accounts made in the hour (from `people.created_at`, so a restart doesn't reopen it; checked again inside the same `INSERT`). Sign-ups go one at a time: `state.sign_ups` is a lock held while the password is scrambled and the account made (with email set up, while the waiting sign-up is saved; finishing makes the account later, without it, the hour's cap checked inside the `INSERT`). Finishing checks the typed password against at most the newest three waiting sign-ups for the address (`WAITING_PER_ADDRESS`), so a wrong try costs at most three checks on sign-in's shared line; a sign-up within a minute of the last link, or past the address's three emails, is kept unemailed (`emailed = 0`) so the link already sent finishes it. Structure change 27 (decision 0125) removed the old `sign_up*` rows in `settings`. New readers' passwords: at least 12 characters (the same as `nine-turtles set-password`), at most 1024 bytes. Only the owner (`people.owner = 1`) may read the readers list (`GET /api/people`: number, email, owner or not, joined; nothing about reading); anyone else gets 403. The owner's Readers page (`GET /api/admin`, decision 0090) is owner-only the same way: app-wide counts, the database's size, whether backups and email are on, the problems logged since start (as on the diagnostics page), and for each reader their email, joined, how many feeds they follow and how many of those keep failing. Counts only: never which feeds, nothing about reading, and not their last-here day (it waits for the owner's answer, `docs/planning/questions.md`).
- **Email** (decision 0088): plain SMTP with `lettre` (`email.rs`), STARTTLS on 587 (or encrypted from the start on 465), refused unencrypted except to the same computer; five `NINE_TURTLES_SMTP_*` settings, all or nothing (the port alone counts as some), and no email at all without them; set without `NINE_TURTLES_PUBLIC_URL`, nine turtles refuses to start. `email::Settings` hides the SMTP password from any debugging print, and a failed send is logged in nine turtles' own words, never the mail server's (which often repeat the address). Only a bare address is accepted anywhere an email is typed (`people::plausible_email`: no name, `<` `>`, quotes, commas, semicolons, colons, brackets, backslashes, spaces or control characters, and lettre's own parse must equal the text), and each email goes to a `Mailbox` built from that parsed address, so `name<someone@example.com>` can't dodge the per-address count. Emails are short plain text, sent behind the answer so timing never says whether one went out; links start with `NINE_TURTLES_PUBLIC_URL`, never a request's address. Tests swap SMTP for an in-memory outbox (`Mailer::outbox`); the browser tests use a made-up mail server on the same computer.
- **Emailed links** (`accounts.rs`, structure change 14; made again by structure change 27, decision 0125, and by structure change 31, decision 0154, which allows `sign-up` lines again: those alone have no `person_id`, and keep the waiting account's scrambled password): an `email_links` table, each link a 32-byte random ticket kept only as a BLAKE2s scramble, used once (`UPDATE … SET used = 1 … RETURNING`, so two presses can't both use it), 24 hours to confirm a changed address or finish a sign-up, 1 hour for a new password and 15 minutes to sign in. The ticket travels in the address's fragment (`/reset-password#ticket=…`, `/confirm-email#ticket=…`, `/sign-in-link#ticket=…`, `/finish-sign-up#ticket=…`): never seen by a server or its logs, read by the page and sent in the POST body. At most three links to one address in any hour, whatever for, and one link of each kind (password, sign-in, change of email, sign-up) a minute (`EMAIL_GAP`, so a second press of Send link sends nothing; decision 0092), and at most three tries to change one reader's email: counted and saved in one `BEGIN IMMEDIATE` transaction (`accounts::make_link`), so requests sent together can't race past either count. A try to change to an address another reader has (or one past its hour's emails) is saved as a spent line with `emailed = 0`: it counts towards the reader's three but never the address's, so neither the answer nor the database work says the address is taken. Expired links are deleted with every new link and every round of background checking (`accounts::tidy_links`), but only once they're also an hour old, so a sign-in link that stopped working after 15 minutes still counts towards its address's three. "Forgot?" (which sends a sign-in link, decision 0122) and the older "Forgot your password?" route always answer the same, after the same database work for an unknown address (`make_no_link`). Using a sign-in link also answers a second random ticket, for choosing a new password: kept only in memory (`accounts::PasswordChoices`, a BLAKE2s scramble per ticket, one hour, tied to the reader and the address the link went to), never in `email_links`, whose checks allow an unemailed line only for a spent change, so no structure change was needed; `/api/password/reset` takes either kind of ticket. A restart forgets every such offer. A new password signs out every device of that reader, deletes their app password, spends their unused sign-in links and ends every offer to choose a password.
- **Pick up where you left off** (decision 0175, `resume.rs`, no structure change): one `person_settings` row, `resume`, holding `article block within` for the article the reader last left part of the way through. `PUT /api/resume` keeps it (only for an article the reader has; `within` from 0 to 1), `DELETE /api/resume?id=` lets it go only if it's still that article (so a device that's behind never forgets a newer place), and `GET /api/resume` answers the article (as in a list), its writer's name (`writers.name`, else `articles.author`) and the place, or `null` for an article now muted or of a feed left. The screen (`web/src/lib/resume.svelte.ts`) keeps it alongside each device's own places (decision 0060) and never says when a request fails.
- **The weekly email** (decisions 0150 and 0184, `weekly.rs`): once a week or off; structure change 43 moved readers who had chosen twice a week to weekly, with a `weekly_moved` row so their next email says so once. Its state is `person_settings` rows named `weekly…` (listed in the module's comment). A background task started at launch (`weekly::run`, only while nine turtles can send email) looks every 10 minutes for readers with a confirmed address (`people.email_confirmed_at`, decision 0154; turning it on refuses an unconfirmed one with `unconfirmed`) whose Saturday 08:00, by the clock offset their browser sent, has passed since they chose and since the last look; it notes the look (`weekly_sent_at`) before sending, so a restart never sends twice, and one reader's database trouble is logged without holding up the rest. Each email's stop link (`/weekly-email#ticket=…`) isn't an `email_links` line: 32 random bytes kept only as a BLAKE2s scramble in `person_settings` (the last ten, comma-separated, so an older email's link still works), sent in the POST body to `POST /api/weekly-email/stop`, which works signed out from nine turtles' own pages. A ticket that isn't one answers 404 `unknown`, so the page never claims it stopped something it didn't; a 256-bit ticket can't be guessed, so that says nothing. Turning it off, either way, removes every `weekly…` row and spends every stop link.
- **Sign-in links** (decision 0096, structure change 20, which made `email_links` again to allow the purpose `sign-in`, copying every line): `POST /api/sign-in/link` (`{email}`, answered 202 whoever asks) and `POST /api/sign-in/link/use` (`{ticket}`). Using one is a single `UPDATE … RETURNING` that also needs the reader to still have the address the link went to (`people.email = email_links.email`), so a changed email leaves earlier links behind; it then signs the device in as a password would (`remember_device`). It bypasses the count of wrong passwords, as the link itself is the proof; the hourly and per-minute email limits are its only limits.
- **Passkeys** (decision 0109, `passkeys.rs`, structure change 25): WebAuthn, checked by webauthn-rs 0.5 (with its `conditional-ui` part). The relying party is `NINE_TURTLES_PUBLIC_URL`'s exact origin, its host the relying party ID; without it, `http://localhost` on any port; a numeric host turns passkeys off. `GET /api/session` says which (`passkeys`: the origin or null), and the page offers passkeys only at that origin in a browser with `PublicKeyCredential`. Adding: `POST /api/passkeys/add` (`{password}`, checked by `auth::ask_password` under the reader's sign-in account, as changing email is) answers a challenge for a discoverable passkey with user verification required (`residentKey: required`, the reader's other passkeys excluded, apart from removed ones, so a device can add again straight after Remove; a re-added removed passkey replaces its removed line); `POST /api/passkeys/add/finish` checks the device's answer and stores the `Passkey` as JSON with its credential number (`UNIQUE`, so one passkey can't be two readers') and the reader's random user handle (a UUID, the same for all their passkeys). Signing in: `POST /api/sign-in/passkey` answers a discoverable challenge (no allowed list; the page picks the browser's sheet or the email field's autofill); `POST /api/sign-in/passkey/finish` finds the passkey by its credential number among those not removed, requires its stored handle to match the one the passkey returns, lets the library check the signature, user verification and counter (a counter that goes backwards is refused), saves the updated counter and `last_used_at`, then `remember_device`, exactly as a password sign-in. Challenges (`passkeys::Ceremonies`) live in memory under a 32-byte random ticket, five minutes, taken out on the first answer whatever it is. Sign-in challenges (open to anyone) and adding challenges (signed-in readers only) are kept apart: at most 1,000 sign-ins wait at once, and a new one pushes out the oldest (expired ones go first), so nobody signed out can switch passkeys off or touch a reader adding one; adding keeps one challenge per reader, and an adding challenge finishes only for the reader who asked. Starting a challenge never answers `wait`. No wrong-try waits: a passkey can't be guessed, and a refused one must never lock the password out; refusals are logged as information. Rename, remove and Undo (`/api/passkeys/{id}/name`, `/remove`, `/undo`) touch only the signed-in reader's lines; removing sets `removed_at` (no longer signs in), Undo clears it within `passkeys::UNDO_FOR` (10 minutes), and older removed lines are deleted when the reader next lists, adds or removes. At most 20 per reader. `passkeys` is in `PER_READER_TABLES`. webauthn-rs links the system's OpenSSL (the Dockerfile installs `libssl-dev` to build and `libssl3t64` to run).
- **The owner's password set by email, and the way back** (decision 0088): a password the owner sets with a link goes in `people.password_hash` and wins over `NINE_TURTLES_PASSWORD_HASH`, but only while that setting stays as it was: the reset saves a BLAKE2s fingerprint of the setting in force (`settings.owner_password_from`, never the line itself), and on every start `auth::owner_password_follows_setting` compares it. If the setting is a real line and its fingerprint differs, the owner's own password is cleared, the fingerprint deleted, every device signed in as the owner signed out and their unused password and sign-in links spent, so the new setting is the owner's password again (`docs/operations/owner-password.md`). A missing or invalid setting changes nothing. Changing email, the owner's too (decision 0125), needs the reader's password, checked as sign-in checks it: the same count of wrong tries (under the reader's email, as a sign-in by email is counted) and the same bounded line of checks for sign-ins by email (`state.password_checks`); it then sends the link to the new address, and tells the old one once it's done. A new password from a link is scrambled only once its ticket is found good, waiting its turn in that same line, so made-up tickets cost the server nothing.
- **The reader's own password** (decision 0200, `own_password.rs`): one `confirm` checks the signed-in reader's password before a change that could hand the account over or can't be undone (a new email, adding a passkey, `POST /api/people/me/delete` and `/api/people/me/data/delete`, each taking `{password}`), counted and queued as sign-in is (`auth::ask_password`; an owner with no email on the owner's own count). `POST /api/people/me/password` (`{current, password}`) and Forgot?'s new password share `store_new` (inside the caller's transaction: the new line, unused `reset` and `sign-in` links spent, every session deleted, the owner's `OWNER_PASSWORD_FROM` fingerprint) and `after_new` (offers to choose a password ended, wrong-try counts cleared); the device that changed it is signed in again.
- **Deleting an account** (`people::delete`): one transaction that first lets go of each feed the reader follows as unsubscribing does (`folders::clear`, their stars included), so a feed nobody else follows stops being checked and its articles nobody has go, then deletes every `email_links` line to the reader's email, then empties `PER_READER_TABLES`, which names every table with a `person_id` column; `server/tests/accounts.rs` reads the tables from `sqlite_master` and fails if one is missing, still holds the reader's lines, or lost any of the owner's, or if `email_links` still holds the reader's email. Never the owner. No password is asked for: the owner's choice (decision 0088).
- **Deleting one's data** (`people::delete_data`, decision 0117): the same transaction as deleting an account (`people::let_go`, shared by both) but only `DATA_TABLES` are emptied (notes, episode progress, entries, subscriptions, writers, rules, folders), then the newsletter feeds the reader still followed (one they stopped keeps its line, so its sender stays away, decision 0091). `ACCOUNT_TABLES` (sign-in, settings, plan, passkeys, assistants, newsletter address) stay. Every table in `PER_READER_TABLES` is in exactly one of the two lists. The owner too. `server/tests/accounts.rs` checks that split, that the data tables are empty, that the account's lines and the owner's are untouched, and that the reader is still signed in.
- Long-lived session cookie per device, each device belonging to one reader (decision 0086) (secure, HTTP-only, SameSite=Strict): a random ticket, of which the database keeps only a scrambled copy. A year from last use. Plus protection against other websites submitting actions on the owner's behalf ("cross-site request forgery"): actions must come from nine turtles' own pages.
- **One tab, one reader** (decision 0121): the web app's `api()` names the reader its tab was opened for in an `x-nine-turtles-reader` header on every request (a tab opened without a connection goes by the device's last reader, `session::deviceReader`). `SignedIn` refuses a request whose header names another reader than the cookie's (409, `x-nine-turtles-other-reader: 1`, `{"error":"other-reader"}`), so a tab left open when another reader signs in on the browser can't save anything as them. On that answer `api()` throws `OtherReader` (never retried, and never handed to callers that read 409 their own way) and sets `updates.otherReader`, which the list's note shows with Reload. Each mark waiting on the device carries the reader whose tab made it (`Mark.reader`); `sendWaiting` drops another reader's instead of sending it. Requests without the header (assistants, a page's first ask) are unaffected.
- A strict Content Security Policy (a browser rule): the browser refuses any script that doesn't come from nine turtles itself. This is a second layer behind sanitizing.
- Failed sign-in attempts are rate-limited for each account on its own (each email in small letters), wherever they come from: five free tries, then a doubling wait up to an hour. At most 4,096 accounts' counts are kept in memory; when full, what would be forgotten anyway goes first, then the quietest account that isn't waiting. Sign-in tries are still decided one at a time, which also slows anyone trying to push a waiting account out by guessing thousands of others.
- Secrets (password hash, diagnostics key, owner report key, backup storage key, SMTP key) come from environment variables, listed in `docs/operations/settings.md`.
- **Other apps' sync, removed** (decision 0184): the Google Reader API at `/api/greader` and its app passwords (decision 0070) went in the owner's review of what to remove; structure change 42 dropped the `app_passwords` table.
- **AI assistants (MCP)** connect at `/mcp` (`server/src/mcp/`: the protocol in `mod.rs`, the list of tools in `tools.rs`, the work in `reading.rs` and `changing.rs`): JSON-RPC over "Streamable HTTP", each POST answered with JSON, no streaming and no session kept. They sign in with OAuth 2.1 (`server/src/assistants.rs`): metadata at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`, dynamic registration at `/oauth/register`, the reader's approval on `/oauth/authorize` (a page of the app), PKCE S256 only, codes (10 minutes) and tickets (access 1 hour, refresh 90 days and rotated) kept only as BLAKE2s scrambles in `assistant_codes` and `assistant_tokens`; or with an assistant key (`nt_` and 64 hex characters, no expiry, a `key` ticket). Each `assistant_connections` line is one reader's. Disconnect sets its `disconnected_at`, which every ticket check refuses from that moment; Undo (`/api/assistants/{id}/reconnect`) clears it within ten minutes, and after that, or at the reader's next disconnect, the line is deleted with its tickets, by the next background round (`assistants/settings.rs`, decision 0238). `/mcp`, `/oauth/token` and `/oauth/register` skip the same-site check (no cookie is used there). Per reader: 60 calls a minute, 3,000 a day, 20 feeds added an hour, counted in memory (`assistants::Limits`). A feed an assistant unsubscribes from gets `subscriptions.kept_until` 30 days on, which `folders::clear_unsubscribed` respects. No library: see `docs/decisions/0111-assistants-mcp.md`.
- The website's feed finder (`/api/find-feeds`, decision 0099) and blog checkup (`/api/checkup`, decision 0178) are the other things anyone may use without signing in; browsers let only nineturtles.app's pages read their answers (CORS; a program can still ask directly, which their shared limits cover), and they never touch the database.
- A public status page (`/status`) says only that nine turtles runs and its version; a diagnostics page (`/diagnostics`) needs a read-only key and never shows the reader's feeds or articles. The owner report (`/owner-report`, decision 0130) needs a key of its own (`NINE_TURTLES_OWNER_REPORT_KEY`, at least 32 characters) and answers "not found" without the setting; it gives counts and dates only, never a name, email, reader number or problem text. Both check the key the same way (`status::key_refused`: a BLAKE2s comparison, so timing gives nothing away).
- Details and rejected alternatives: `docs/decisions/0010-sign-in.md`, `docs/decisions/0087-sign-in-by-email.md`, `docs/decisions/0088-account-emails.md` and `docs/decisions/0109-passkey-sign-in.md`.

## Part 4: Automatic checks

Wherever a principle can be checked by a computer, it is. These run on every pull request, all through `scripts/check.sh`, in parts side by side (decision 0065; what each step does: `docs/operations/checks.md`). A pull request that changes only documents skips all but the quick ones:

| Principle | Check |
|---|---|
| The computer checks the work | Rust: format, lint and tests. Frontend: type check and tests. Every pull request except documents-only changes and tiny fixes also gets a second-agent review. A test never depends on how fast the computer is; one that fails now and then is fixed, never retried until it passes (no automatic retries, decision 0114). |
| Owner can see the change | Screenshots of every screen on White and Night (Paper on the list, article, Settings and Edit screens), at desktop and phone width, attached to each pull request |
| Libraries stay safe | A weekly report of known security problems in our libraries. It only reports; nothing is updated automatically. |
| First floor (accessibility) | Automated accessibility and contrast tests on every screen, on every page (White, Paper and Night) |
| No motion (DESIGN.md) | Fails if animations or transitions appear in the styles |
| Written for the next agent | Fails if a file of the app's own code grows past 800 lines (a few older, longer files may only shrink), or if a file, an export or a server `pub` item is unused (decision 0126) |
| Fast by design | Fails if the frontend download grows past its size budget |
| Docs stay findable | Fails if a document links to a file that doesn't exist; runs on every pull request, documents-only ones too (decision 0119) |
| Never add a library without asking | Fails if the code uses a library that isn't on the approved list in `docs/libraries.md`. Agents add to that list only after the owner has said yes. |
| Publisher floor | Tests confirm conditional requests, backoff and that no article pages are fetched |
| Search for Hindi | Tests search Hindi text and find the right results |
| Data floor | Database changes are tested against a copy of real-shaped data |
| Fast at real size | Speed tests run against a made-up database the size of 500 feeds and a year of articles |
| Keyboard floor | Every feature has tests that use it with the keyboard only |
